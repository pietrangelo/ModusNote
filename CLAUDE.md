# ModusNote

## MISSION
Costruire un'applicazione mobile e web offline-first e crittografata end-to-end (E2EE) con motore a tipi dinamici (schemi estensibili per canzoni, sogni, to-do, note libere) e gestione di blob audio cifrati, sincronizzabile in gruppi a zero-knowledge.

- **Stack:** Flutter (Dart 3.13+), pub workspace. Un'unica app per Android, iOS e **web** (Flutter Web, WebAssembly), che riusa gli stessi pacchetti di dominio.
- **Dominio dell'app:** `modus.serv.run`. Identificativo Android/iOS: `run.serv.modus`.
- **Lingue:** l'app è multi-lingua fin dal primo commit (italiano e inglese per iniziare).

## 0. STRUTTURA DEL REPOSITORY E COMANDI

```text
apps/modusnote/                      Shell Flutter (Android, iOS, web): UI, l10n, wiring degli adapter. Nessuna logica di dominio.
packages/identity_cryptography/      Bounded context (dominio puro)
packages/schema_dynamic_content/     Bounded context (dominio puro)
packages/blob_storage_media/         Bounded context (dominio puro)
packages/collaboration_access_control/ Bounded context (dominio puro)
packages/offline_sync/               Bounded context (dominio puro): revisioni firmate, conflitti, coda offline
packages/identity_cryptography_adapters/ Adapter libsodium (pacchetto `sodium`, variante sumo per Argon2id); passkey WebAuthn con PRF sul web (`web_passkeys.dart`)
packages/blob_storage_media_adapters/  Storage dei blob cifrati (filesystem tramite `package:file`), muxer Ogg Opus, encoder libopus (FFI + build hook)
packages/blob_storage_media_recorder_adapters/ Microfono tramite il plugin `record` (pacchetto Flutter, test con `flutter test`)
packages/offline_sync_adapters/      Database locale SQLite (stessa API nativa e WASM): solo buste cifrate; `SupabaseSyncServer` (PostgREST via `package:http`)
packages/<context>_adapters/         Altri petali esterni, creati quando servono
tool/architecture_guard/             Verifica statica delle regole della rosetta
```

Ogni pacchetto di dominio ha la stessa forma:

```text
lib/<context>.dart        API pubblica: l'unico file che altri pacchetti possono importare
lib/src/core/             Entities e Value Object immutabili. Solo dart:core/typed_data/collection/math/convert e package:meta.
lib/src/application/      Use Case e Port. Può usare core e dart:async, nient'altro.
```

Gli adapter **non** vivono in `lib/src/adapters/` del pacchetto di dominio: vanno in un pacchetto separato `<context>_adapters`, così le dipendenze di framework non possono entrare nel dominio nemmeno per sbaglio. `tool/architecture_guard` fa fallire la CI se:
- `core` importa qualcosa al di fuori di `core` e delle librerie consentite;
- `application` importa framework, I/O o pacchetti di terze parti;
- un pacchetto di dominio dichiara dipendenze diverse da `meta` o da altri pacchetti di dominio;
- un pacchetto importa i file `src/` di un altro pacchetto.

`core` e `application` possono importare l'API pubblica (`lib/<context>.dart`) di un altro pacchetto di dominio dichiarato in `dependencies`, mai quella di un pacchetto `_adapters`.

Comandi (dalla radice):


### Localizzazione
- Le stringhe dell'app vivono in `apps/modusnote/lib/l10n/app_<lingua>.arb` (template `app_en.arb`). Nessuna stringa visibile all'utente scritta a mano nei widget.
- Il dominio non contiene testo localizzato. Gli schemi seed referenziano le etichette dei campi tramite **chiavi** (es. `schema.song_sketch.field.bpm`), che la UI risolve con `AppLocalizations`. Gli schemi creati dall'utente portano l'etichetta scritta dall'utente così com'è.
- Una nuova lingua si aggiunge con un nuovo file ARB e, su iOS, una voce in `CFBundleLocalizations` di `ios/Runner/Info.plist`.

- I valori vivono in un unico set di design token (`apps/modusnote/lib/theme/`); i widget non scrivono numeri a mano. I test di componente verificano che le dimensioni usate appartengano alla scala.

### Client web
Il client web è un'alternativa completa all'app mobile e si sincronizza con essa: per il protocollo di sync è semplicemente un altro dispositivo del vault, con la propria coppia di chiavi di identità. Si compila con `flutter build web --wasm --csp --no-web-resources-cdn` seguito da `dart run tool/finalize_web_build.dart` (da `apps/modusnote`) (nessuna risorsa caricata da CDN di terzi: CanvasKit e font fanno parte del bundle servito da Cloudflare Pages).

Nel browser alcune garanzie cambiano, e il codice deve tenerne conto in modo esplicito:
* **Memoria delle chiavi:** non esistono `sodium_malloc`/`mlock`. Su web `SecureKey` è un buffer JS che viene azzerato al `dispose()`, ma il motore JS può averne fatto copie. La regola "dispose il prima possibile" resta, ma la garanzia è più debole che su mobile.
* **Fiducia nel codice:** il server che distribuisce l'app web potrebbe servire codice malevolo a ogni caricamento. Mitigazioni obbligatorie: Content-Security-Policy restrittiva (niente script inline o di terze parti, solo `wasm-unsafe-eval`), Subresource Integrity, nessuna dipendenza da CDN, hash delle build pubblicati.
* **XSS ed estensioni:** qualunque script iniettato vede le chiavi in memoria. Niente HTML generato da contenuti utente (Markdown e testo arricchito sono renderizzati come widget, mai come HTML).
* **Persistenza:** niente SQLCipher. Il database locale è SQLite WASM su OPFS/IndexedDB e contiene solo record già cifrati con le buste del dominio. Le chiavi non si salvano mai in `localStorage`/IndexedDB in chiaro.
* **Sblocco:** niente biometria nativa. Il vault si apre con la passphrase oppure con una passkey (WebAuthn con estensione PRF), dove disponibile: vedi "Passkey nel browser".
* **Passkey nel browser (Fase 7.4, 2026-10-13):** a vault aperto il pulsante con l'impronta nella libreria registra una passkey (`WebAuthnPasskeyPrf` in `identity_cryptography_adapters/lib/web_passkeys.dart`, port `PasskeyPrf`): relying party = dominio della pagina, `userVerification: 'required'` sempre (CTAP2 `hmac-secret` ha un segreto separato per l'uso verificato), user handle casuale, nessuna attestazione né server. L'uscita PRF sul `PrfSalt` casuale entra subito in una chiave libsodium e il buffer del browser viene azzerato. Non serve la MasterKey: `VaultKeeper.enrollPasskey` sigilla di nuovo l'identità sotto una sottochiave della PRF (`crypto_kdf`, contesto `mn-passk`) e la chiave locale con `KeyEncapsulation` verso l'identità stessa, in un `PasskeySlot` (tabella `vault_passkey`, schema locale v3) i cui dati associati legano id della passkey, salt, `SubkeyId` e tutti i campi in chiaro del `VaultHeader`; l'identità aperta deve essere il fondatore dell'header. Uno slot copiato da un altro vault, un header modificato o un'altra passkey danno `PasskeyRejectedException`. Una sola passkey per dispositivo: registrarne un'altra o disattivarla chiede al gestore di dimenticare la vecchia (`signalUnknownCredential`, se c'è). La passphrase resta sempre valida. Dove `getClientCapabilities` esclude la PRF il pulsante non compare; se la passkey scelta non ha PRF l'app lo dice. Su mobile il port non c'è (`passkeys: null`).
* **Crypto:** libsodium arriva via WebAssembly (backend JS del pacchetto `sodium`, variante sumo per Argon2id). Non si usa WebCrypto, che non offre XChaCha20-Poly1305 né Argon2id.
* **Vault nel browser (Fase 7.1, 2026-10-12):** `lib/bootstrap/home_web.dart` costruisce lo stesso `VaultKeeper` del mobile (`vault_wiring.dart`, Argon2id `moderate`, circa 1,5 s in Chromium). `web/sodium.js` (libsodium.js sumo, SHA-512 verificato dal pacchetto `sodium`) e `web/sqlite3.wasm` (SHA-256 fissato) sono committati e serviti dalla nostra origine; si aggiornano solo con `apps/modusnote/tool/fetch_web_assets.sh` quando cambiano le versioni dei pacchetti, e `test/platform/web_assets_test.dart` fallisce se non corrispondono. Il database è `/vault.sqlite` su `IndexedDbFileSystem` (OPFS sincrono esiste solo nei worker); le scritture arrivano a IndexedDB in background e vengono forzate quando la scheda si nasconde.
* **Audio nel browser (Fase 7.3, 2026-10-12):** i blob cifrati stanno in un secondo database IndexedDB, `modusnote-blobs` (`IndexedDbCiphertextBlobStore` in `blob_storage_media_adapters/lib/web_media.dart`): un pezzo per `[id, indice]` e uno stato per blob ("in scrittura" o numero di pezzi), quindi il commit è una sola scrittura e le registrazioni interrotte da una scheda chiusa si scartano all'avvio. IndexedDB clona un typed array con tutto il suo buffer, per cui una vista viene sempre copiata prima di salvarla. Il microfono passa dal worklet di `record` (PCM, nessun file); `WebCodecsOpusEncoder` comprime in Opus con l'`AudioEncoder` del browser e il nostro `OggOpusMuxer` (pre-skip dall'OpusHead del browser), quindi una registrazione web è lo stesso Ogg Opus dei telefoni. Dove WebCodecs manca si registra in WAV. `WebCodecsOpusDecoder` riproduce sia le registrazioni web sia quelle dei telefoni (prova con un file libopus fisso nei test), dopo il nostro demuxer. `WebAudioRecordingPlayer` (`lib/audio/web_audio_player.dart`) tiene i campioni in PCM16 e programma segmenti di 5 s di Web Audio: niente URL, elementi `<audio>` o file. I binding WebCodecs sono nostri (`webcodecs.dart`), perché `package:web` 1.1 ha solo la parte video; i buffer che il browser deve riempire si allocano in JS, perché sotto WebAssembly `toJS` su una lista Dart ne passa una copia. Test in Chrome con dart2js e dart2wasm (`test/web`); la prova end-to-end registra dal microfono finto di Chrome, ricarica, riproduce e verifica che nessun blob contenga `OggS`, `OpusHead` o `RIFF` in chiaro.
* **CSP e integrità (Fase 7.2, 2026-10-12):** `web/_headers` vieta tutto tranne la nostra origine: `script-src 'self' 'wasm-unsafe-eval'`, niente `unsafe-inline`/`unsafe-eval`, stili inline solo per hash (i due `<style>` che il motore Flutter inserisce, il cui testo cambia per browser, Chrome, Edge, Firefox e Safari, e per build, WebAssembly o JavaScript: `web_headers_test` ricostruisce ogni variante e ne verifica l'hash; cambiano anche con le versioni di Flutter e la prova end-to-end in Chrome lo segnala; più lo `<style>` vuoto che `SelectionArea` dell'anteprima Markdown crea e poi riempie via CSSOM, senza il quale l'anteprima non si disegna), `connect-src` limitato alla nostra origine, al progetto Supabase e all'endpoint R2 dell'account (origini esatte, nessun carattere jolly), isolamento cross-origin (COOP/COEP/CORP), `frame-ancestors 'none'`. Trusted Types obbligatori: `flutter-js` è la policy di Flutter, `default` è `web/trusted_types.js`, caricato per primo, che concede URL di script solo della nostra origine o dei suoi blob (il caricatore dei worker di skwasm non usa una policy propria) e rifiuta sempre HTML e script da stringhe. Niente service worker (`web/flutter_bootstrap.js`). `tool/finalize_web_build.dart` aggiunge SRI (sha384) agli script di `index.html`, rifiuta script inline o di altre origini e scrive `SHA256SUMS` di tutto il bundle; la CI lo pubblica nel riepilogo del job e carica il bundle come artifact. `tool/web_e2e` (Playwright, versione e lockfile fissati, Chrome di sistema) serve la build con i suoi header su `localhost` (WebAuthn rifiuta gli indirizzi IP come relying party) e, sia per la build WebAssembly sia per quella JavaScript, crea il vault, salva una nota, ricarica, prova una passphrase sbagliata e quella giusta, attiva una passkey sull'autenticatore virtuale di Chrome (CDP `WebAuthn`, con PRF) e riapre il vault con quella, e verifica zero violazioni CSP, zero errori, nessuna richiesta fuori dall'origine e solo ciphertext in IndexedDB. Test: `web_headers_test.dart`, `web_build_test.dart`.
* **Interi a 64 bit (2026-10-12):** la build web ricade su dart2js nei browser senza WasmGC, dove `ByteData.setInt64`/`getInt64` non esistono e gli interi sono esatti solo fino a 2^53. I formati binari del dominio scrivono quindi gli interi a 8 byte con `setPortableInt64`/`getPortableInt64` (`portable_int64.dart`, due metà da 32 bit, stessi byte di `setInt64`) e rifiutano valori oltre ±(2^53 − 1), così ogni piattaforma legge lo stesso numero o rifiuta l'input. Mai usare le funzioni Int64 di `ByteData` nel codice che gira sul web (le helper accettano anche `Endian.little`, usato per i granule Ogg); i test `portable_int64_test.dart` e quelli del muxer e demuxer Ogg girano anche in Chrome in CI.

### Codice per piattaforma (mobile e web)
Il dominio non sa su quale piattaforma gira. Le differenze tra Dart nativo (VM/AOT, `dart:io`, `dart:ffi`) e web (JS/WASM, `dart:js_interop`) restano negli adapter:
* **Ports & Adapters + conditional imports.** Quando un adapter ha bisogno di API diverse per piattaforma, il pacchetto `<context>_adapters` espone una factory che sceglie l'implementazione con `import 'x_stub.dart' if (dart.library.io) 'x_native.dart' if (dart.library.js_interop) 'x_web.dart';`. Lo stub lancia `UnsupportedError`. Nei pacchetti di dominio i conditional imports sono vietati (regola `conditionalImport` dell'architecture guard).
* **libsodium.** L'app usa direttamente il pacchetto `sodium` 4, che compila libsodium con il proprio build hook su Android, iOS e desktop (Flutter esegue gli hook da solo); sul web arriverà `sodium.js` sumo con `dart run sodium:update_web --sumo` (Fase 7). `sodium_libs` non serve più. Gli adapter ricevono l'istanza `SodiumSumo` già inizializzata nel costruttore. L'inizializzazione (asincrona sul web, per caricare il WASM) avviene una sola volta all'avvio dell'app in `lib/bootstrap/`, quindi non esiste un adapter "non ancora inizializzato".
* **Le API crypto restano quelle del dominio.** Si usano solo i port `EnvelopeEncryptor` e `KeyDerivationService`: XChaCha20-Poly1305 AEAD con `AssociatedData` obbligatoria, nonce generato dall'adapter e chiavi come handle opachi (`SymmetricKey`). Non si usano `secretBox` (nessun dato associato, quindi nessun legame al record), né chiavi o nonce passati come `Uint8List`.
* **Audio come flusso di byte, mai come percorso di file.** Il port di registrazione restituisce `Stream<Uint8List>`, con chunk cifrati appena prodotti, così su nessuna piattaforma esistono file audio in chiaro. Implementazione con il pacchetto `record` (`startStream`). Nota: lo streaming di `record` produce PCM, quindi la compressione Opus va fatta dall'adapter (libopus via FFI su mobile, WebCodecs `AudioEncoder` su web). Safari non registra Opus/WebM con `MediaRecorder`; il formato effettivo va negoziato per piattaforma e salvato nei metadati cifrati del blob.
* **Permessi microfono:** Android `RECORD_AUDIO` in `AndroidManifest.xml`; iOS `NSMicrophoneUsageDescription` in `Info.plist`, localizzata in `ios/Runner/<lingua>.lproj/InfoPlist.strings`; web nessun manifest, ma solo su HTTPS (o `localhost`), con richiesta del browser a runtime.
* **Opus (decisione del 2026-10-11):** libopus si compila dai sorgenti ufficiali tramite il build hook di `blob_storage_media_adapters` (versione e SHA-256 fissati in `hook/build.dart`; la CI confronta l'hash con `SHA256SUMS.txt` di xiph.org). I binding FFI sono nostri e minimi, e i `ctl` variadici passano da un piccolo shim C. Nessun wrapper di terze parti. Per build offline: `MODUSNOTE_OPUS_ARCHIVE=/percorso/opus-<versione>.tar.gz` (l'hash viene verificato comunque). Sul web l'Opus arriva da WebCodecs (vedi "Audio nel browser"); dove manca, la cattura produce WAV PCM16 non compresso.

### Infrastruttura (decisione del 2026-10-11)
| Componente | Servizio | Cosa vede il servizio |
|---|---|---|
| Client web | **Cloudflare Pages** (file statici; build in GitHub Actions, perché l'ambiente di build di Pages non include Flutter, poi `wrangler pages deploy`) | Solo il bundle dell'app |
| Blob audio cifrati | **Cloudflare R2** (S3-compatibile, nessun costo di egress) | Solo chunk `.enc` e la loro dimensione |
| Sync e account | **Supabase** (PostgreSQL + Auth) | Righe cifrate, id, revisioni, timestamp; l'email dell'account |

L'invariante zero-knowledge vale per tutti e tre i servizi: ricevono e restituiscono solo ciphertext prodotto dalle buste del dominio. Regole che ne derivano:
* **Auth e chiavi sono separati.** Supabase Auth autentica l'account (email/magic link o OAuth) per l'accesso alle righe. La passphrase del vault non viene mai inviata, né usata come password di Supabase. Se in futuro si userà un'unica password, la credenziale di login deve essere derivata dalla chiave Argon2id con una derivazione separata (KDF con contesto diverso), mai la passphrase stessa.
* **Row Level Security** obbligatoria su ogni tabella: un utente legge e scrive solo le righe dei vault di cui è membro.
* **Metadati minimi in chiaro:** id opachi, revisione, timestamp di sync, dimensione. Titoli, tipi di nota, tag e schemi stanno solo dentro i payload cifrati.
* **R2 tramite URL pre-firmati** emessi da una funzione lato server (Supabase Edge Function o Cloudflare Worker) dopo il controllo dell'autorizzazione. Le credenziali R2 non arrivano mai al client. CORS limitato al dominio dell'app.
* **Deploy (2026-10-13):** progetto Supabase `oobxqzjzauhmurvxvhuo` (eu-central-1) con le migrazioni e la funzione `blob-url` (verify JWT attivo); bucket R2 `modusnote-blobs` nell'account `9bc65f198cf14dc51e892d6657550260`. I segreti `R2_*` della funzione, la chiave R2 limitata al bucket, il CORS del bucket e i modelli email «Magic Link» e «Confirm signup» con `{{ .Token }}` si impostano a mano dalle dashboard. `.github/workflows/deploy-web.yml` pubblica il client web su Cloudflare Pages (progetto `modusnote`, `wrangler` installato con `npm ci` dal lockfile di `tool/deploy`, mai con `npx`) dopo ogni CI verde su `main`, con URL e chiave publishable compilati nel bundle e la lista SHA-256 nel riepilogo del job; servono i segreti del repository `CLOUDFLARE_API_TOKEN` (solo Pages: Edit) e `CLOUDFLARE_ACCOUNT_ID`.

* **Schema (`supabase/migrations/`):** `workspaces`, `workspace_accounts` (account Supabase ammessi, con `can_manage` e `can_write`), e tre flussi **append-only**: `sync_rows` (record_id, epoca, ciphertext), `membership_records` (registro firmato, `sequence` univoca) e `key_bundles`. Nessun client può fare UPDATE o DELETE sui flussi, nemmeno con una policy aggiunta per errore, perché il privilegio è revocato; l'unica cancellazione è quella delle revisioni superate, fatta da un trigger (vedi "Compattazione delle revisioni"). Le posizioni sono assegnate dal server per workspace sotto lock, quindi crescono in ordine di commit e un client che legge `position > cursore` non salta righe. Revocare un dispositivo significa anche togliere il suo account da `workspace_accounts` (`remove_member`, vedi «Inviti tra account»). Solo `delete_account()` (vedi "Eliminazione dell'account") cancella un workspace intero. `device_links` (migrazione `20261013000000_device_links.sql`) è l'unica tabella da cui i client cancellano: offerta e risposta di un collegamento tra dispositivi, leggibili solo dall'account che le ha scritte e solo per 15 minuti; il client sceglie solo `link_id`, tipo e payload (privilegio di INSERT per colonna), così una riga non può essere datata nel futuro.
* **Cosa può aggiungere un account (2026-10-18, test di sicurezza):** il server agisce su alcune righe prima che un client le verifichi, quindi non basta che i client scartino quelle non firmate. Solo un account che gestisce (`can_manage`) aggiunge record a `membership_records` e `KeyBundle`, e un record prende solo la `sequence` successiva (trigger `next_membership_sequence`; ripetere quella già presente resta un 409): prima qualunque account del workspace, anche chi era invitato a leggere, poteva occupare il numero successivo (o uno lontanissimo) con un record illeggibile, e il registro restava bloccato per tutti, rimozione compresa. Solo un account che scrive (`can_write`, o che gestisce: `writes_workspace`) aggiunge righe a `sync_rows`, perché la compattazione cancella le righe superate prima che i client scartino la riga di un lettore, e carica o cancella blob (`reserve_blob_upload`, `blob-url`). `admit_member(..., write)` è falso solo per chi entra come «Può leggere» (`SyncEngine.admit` passa `Role.writesContent`, il client manda `write` solo quando è falso, così un server vecchio continua a funzionare per gli altri ruoli); un account tiene il massimo dei ruoli dei suoi membri. Un dispositivo che può solo leggere non pota i blob su R2 (`BlobSync.canPrune`). Migrazione `20261018000000_member_capabilities.sql`, da applicare prima della funzione `blob-url` aggiornata. **Limite noto:** gli account entrati prima di questa migrazione scrivono tutti; chi aveva invitato una persona a leggere imposta `can_write = false` dal SQL editor.

* **Adapter Dart (`SupabaseSyncServer`):** parla con PostgREST (`/rest/v1/<tabella>`) tramite `package:http`, con la chiave anon pubblica e il token di sessione Supabase passato come callback (mai salvato né incluso nei messaggi d'errore). I `bytea` viaggiano come `\x` esadecimale. Le risposte sono input non fidato: posizioni non strettamente crescenti o registro di membership con buchi danno `MalformedSyncDataException`, una voce illeggibile viene scartata. Errori di rete, timeout, 5xx, 408 e 429 diventano `ServerUnavailableException` (il motore resta offline e riprova); gli altri rifiuti `SyncServerRejectedException(status)`. `supabase/tests/e2e.sh` lo prova contro PostgREST v12 e PostgreSQL veri (RLS, trigger, formati), anche in CI.
* **Compattazione delle revisioni (2026-10-14):** ogni salvataggio sincronizzato è una riga di `sync_rows`, ma a un dispositivo serve solo la revisione che vince per ogni record. Il server non sa quale sia (vettori e orari sono sigillati), l'autore sì: ogni riga inviata porta in chiaro `supersedes`, la posizione fino alla quale tutte le righe del suo record sono superate da lei, e il trigger `drop_superseded_rows` (migrazione `20261014100000_sync_compaction.sql`, security definer) le cancella nella stessa transazione, solo dello stesso workspace e record e sotto la posizione della riga nuova. Lo spazio cresce quindi con le note, non con le modifiche. Il valore si annota in `SyncEngine.write`, non all'invio (un pull nel frattempo può portare una revisione concorrente che quella nuova non ha visto): è il cursore di pull letto prima del record locale, fermato prima della prima riga di quel record che il dispositivo non ha saputo aprire (`LocalRecordStore.markUnreadable`, tabella `unreadable_rows`, colonna `supersedes` della coda: schema locale v5). Perché togliere righe superate non cambi mai il vincitore, ogni revisione è scritta dopo tutte quelle che il suo autore ha visto, anche con l'orologio indietro (`LocalRecord.latest`, un microsecondo dopo; massimo 2^53 − 1 µs): così last-writer-wins è un ordine totale coerente con la causalità e un dispositivo che vede solo le righe rimaste sceglie lo stesso vincitore di chi le ha viste tutte. `SupabaseSyncServer` invia sempre `supersedes` (0 non cancella nulla), quindi la migrazione va applicata prima di distribuire l'app. **Limiti noti:** sul server non resta la cronologia delle revisioni; un membro che dichiara un `supersedes` falso nasconde le revisioni più vecchie di quel record ai dispositivi che non le hanno ancora scaricate (può già far vincere la propria con un orario futuro o un tombstone); un dispositivo revocato che usa ancora lo stesso account Supabase può fare lo stesso, perché la revoca è nelle chiavi e nel registro, non nell'accesso al server; le righe scritte prima di questa versione si compattano alla modifica successiva della loro nota. Test: `sync_engine_test.dart` (gruppo `compaction`), `supabase/tests/rls_test.sql`, `supabase_e2e_test.dart`.
* **Controllo delle novità in una richiesta (2026-10-15):** a vault aperto ogni dispositivo sincronizza ogni minuto e quasi sempre non trova nulla. `SyncEngine.sync` chiede prima `SyncServer.heads` (la funzione `sync_heads(workspace)`, migrazione `20261015000000_sync_heads.sql`, security invoker: posizione più alta di righe e `KeyBundle` e numero di record del registro, letti dalle chiavi primarie) e legge solo i flussi più avanti dei suoi cursori, quindi un giro a vuoto è una richiesta invece di tre. Un non membro vede zeri, come un workspace vuoto. Un server senza la funzione risponde 404 e `heads` vale `null`: il dispositivo chiede tutto come prima, quindi app e migrazione si distribuiscono in qualunque ordine. Un server che dichiara posizioni più basse può solo ritardare quello che già potrebbe trattenere. Un gateway su Cloudflare Workers con KV o D1 è stato valutato e scartato (2026-10-15): le note si aprono dal vault locale, la domanda «cosa è cambiato dopo X» era già una lettura dell'indice in meno di mezzo millisecondo, il Worker dovrebbe comunque chiedere a Supabase JWT e appartenenza (o ritardare la revoca con una cache), KV gratuito ha 1.000 scritture al giorno ed è consistente solo dopo fino a 60 s. Test: `sync_engine_test.dart` (gruppo `heads`), `supabase_sync_server_test.dart`, `supabase/tests/rls_test.sql`, `supabase_e2e_test.dart`.
* **Quote contro l'abuso (2026-10-14):** chiunque può creare un account, quindi il server limita quanto un account gli fa tenere; non guarda dentro i dati, li conta (migrazione `20261014200000_quotas.sql`). I limiti stanno nella tabella `quotas` (nessun accesso per i client) e si cambiano con un `UPDATE` dal SQL editor, senza migrazione: 100 MiB di ciphertext nei tre flussi di tutti i workspace fondati da un account (`account_bytes`: i dispositivi che ammette scrivono sul suo conto), 20 workspace fondati per account (ogni vault nuovo ne fonda uno e quello abbandonato resta, quindi è solo un argine), 10 account per workspace, 20 righe `device_links` per account in 15 minuti (le sue righe scadute si cancellano a ogni inserimento), un blob al più 512 MiB e 2 GiB al giorno di caricamenti su R2 per account. I byte per workspace li tiene `workspace_usage` con trigger su inserimenti e cancellazioni; il controllo gira dopo la compattazione (i trigger vanno in ordine di nome), quindi una modifica che non fa crescere la nota passa sempre, anche a quota piena. Il rifiuto è SQLSTATE `PT413` o `PT429`, che PostgREST rende HTTP 413 o 429: 413 diventa `SyncProblem.full` («spazio esaurito» nel foglio Sincronizzazione, la coda resta sul dispositivo), 429 vale come offline. Per R2 `blob-url` chiede `reserve_blob_upload(workspace, blob, size)` *come il chiamante* prima di firmare un `PUT` (403 non membro, 413 troppo grande, 429 budget del giorno finito; lo stesso blob ripetuto conta una volta) e firma `Content-Length` nell'URL, così R2 rifiuta un corpo di un'altra lunghezza; il client manda `size` (`R2RemoteBlobStore.upload`) e un `PUT` senza `size` è un 400. Chiamare `reserve_blob_upload` direttamente consuma solo il proprio budget. **Ordine di deploy:** migrazione, poi l'app (il client web e quello Android mandano `size`, che la funzione vecchia ignora), poi la funzione `blob-url`: un'app vecchia non carica più registrazioni finché non si aggiorna. **Limiti noti:** non c'è un tetto allo spazio totale su R2 per workspace (solo il budget giornaliero; la pulizia dei blob non citati recupera quello che nessuna nota usa); un account che lascia un workspace che ha fondato continua a pagarne i byte; il rifiuto di un corpo di lunghezza diversa da quella firmata va confermato su R2 al primo deploy; i limiti dell'auth (email e codici all'ora, per IP) si impostano dalla dashboard di Supabase, Authentication > Rate Limits. Test: `supabase/tests/rls_test.sql`, `supabase_e2e_test.dart`, `blob-url/handler_test.ts`, `sync_controller_test.dart`.
* **URL pre-firmati per R2 (`supabase/functions/blob-url`):** Edge Function senza dipendenze di terzi (firma SigV4 scritta con WebCrypto e verificata sul vettore d'esempio di AWS). Riceve `{workspace_id, blob_id, method}` con il token di sessione, chiede al database `is_workspace_account` *come il chiamante* (lo stesso helper delle policy RLS) e restituisce un URL valido 5 minuti per l'unico oggetto `<workspace>/<blob>.enc`. `GET` per leggere (anche a intervalli con `Range`), `PUT` solo per creare: l'URL è firmato con `If-None-Match: *`, quindi un `PUT` non sovrascrive un oggetto esistente; un membro che scrive può però cancellarlo e caricarne un altro, che i dispositivi rifiutano perché non ha il digest scritto nella nota (vedi «Registrazioni su R2»). Cancellare ed elencare (2026-10-14) la funzione lo fa da sé, con la firma SigV4 nell'header `Authorization` (R2 pre-firma solo operazioni sugli oggetti; vettore AWS «GET Bucket» nei test), e non consegna mai un URL che cancella: `{workspace_id, method: "DELETE", blob_ids}` (da 1 a 50 id, ogni oggetto `<workspace>/<blob>.enc`; 404 vale come cancellato) e `{workspace_id, method: "LIST", cursor?}` (ListObjectsV2 con prefisso `<workspace>/`, al più 1000 per pagina; restituisce solo id, dimensione e ora di caricamento delle chiavi `<workspace>/<id>.enc` ben formate, più il cursore opaco di R2). `GET` e `LIST` chiedono `is_workspace_account`, `PUT` e `DELETE` `writes_workspace` (un account che può solo leggere non carica né cancella): ogni membro che scrive può cancellare qualunque blob del workspace, come può già scrivere un tombstone per qualunque nota; chi non è membro non può né cancellare né elencare. Un errore di R2 è un 503 (il client riprova; cancellare è idempotente). I segreti `R2_*` si impostano con `supabase secrets set` e non lasciano mai la funzione; le risposte hanno messaggi fissi; CORS solo per `APP_ORIGIN` (predefinito `https://modus.serv.run`). Il CORS del bucket R2 deve ammettere la stessa origine e l'header `If-None-Match`. Limiti noti: un URL `PUT` pre-firmato non può imporre una dimensione massima (resta il limite di R2), e il rifiuto di sovrascrittura va confermato su un bucket reale al primo deploy.

### Vault del dispositivo
* **`VaultKeeper`:** `create` fonda uno spazio personale con una nuova identità di dispositivo, `unlock` lo riapre. La passphrase diventa la MasterKey (Argon2id) ed è consumata da ogni chiamata. La MasterKey sigilla l'identità e deriva la chiave locale dei record (`crypto_kdf`, contesto `mn-local`), poi viene rilasciata subito.
* **`VaultHeader`:** l'unico dato del vault in chiaro (salt, costi Argon2id entro soglia minima e massima, workspace, fondatore, `SubkeyId` della chiave locale, identità sigillata; un dispositivo che si è unito a un workspace scrive la versione 2 con il proprio `member`, mentre l'header del fondatore resta byte per byte quello di sempre). Tutti i campi sono legati ai dati associati dell'identità, quindi un header alterato si comporta come una passphrase sbagliata (`WrongPassphraseException`).
* **Registro locale:** registro dei membri e `KeyBundle` salvati sul dispositivo (`SqliteVaultStore`, stesso file SQLite dei record, schema versionato in comune) vengono riverificati a ogni sblocco a partire dal fondatore dell'header. Quello che il `SyncEngine` verifica dopo (record nuovi del registro, `KeyBundle` che concedono chiavi a questo dispositivo) si aggiunge con `appendMembership` e `appendKeyBundles`, così il vault si riapre offline sapendo tutto. `lock()` rilascia identità, chiave locale e GroupKey.
* **Passphrase non recuperabile (2026-10-15):** dove si sceglie una passphrase (creazione del vault in `VaultGate`, collegamento in `JoinVaultScreen`) `PassphraseWarning` (`lib/vault/passphrase_warning.dart`) dice in un riquadro oro che la passphrase non lascia mai il dispositivo e che nessuno, nemmeno chi ha creato l'app, può reimpostarla o recuperare le note; il pulsante resta disattivato finché la persona non spunta di aver capito. Lo sblocco non lo mostra.
* **Limite noto (Flutter):** la passphrase digitata passa per la `String` di un `TextField`, inevitabile. La UI la converte subito in `PasswordSecret` e svuota il controller.
* **App (`lib/vault/`, `lib/bootstrap/`):** su mobile `VaultGate` chiede di creare il vault al primo avvio e la passphrase ai successivi, e mostra le note solo a vault aperto; il pulsante "Blocca" rilascia le chiavi. `VaultNoteStore` salva ogni nota come documento `EntryCodec` in un record del `SyncEngine` (l'id della nota è l'id del record, 32 cifre esadecimali) e scarta i record che non decodificano, non rispettano lo schema o portano l'id di un altro record. Un avviso nella libreria (`UnreadableNotice`) dice quante note richiedono una versione più recente dell'app. Il database è `vault.sqlite` nella cartella di supporto privata dell'app; il vault mobile usa Argon2id `moderate`. Senza progetto Supabase configurato il server di sync è `OfflineSyncServer`, sempre irraggiungibile: le modifiche restano nella coda, già sigillate (vedi "Account e sincronizzazione"). Sul web (Fase 7.1) lo stesso vault vive in IndexedDB: vedi "Vault nel browser".
* **Account e sincronizzazione (2026-10-13):** il progetto si fissa alla build con `--dart-define=MODUSNOTE_SUPABASE_URL=https://<progetto>.supabase.co` e `--dart-define=MODUSNOTE_SUPABASE_ANON_KEY=<chiave publishable>` (`lib/sync/sync_config.dart`: solo HTTPS, o HTTP verso `localhost`; senza i due valori niente account e niente pulsante). La chiave publishable è pubblica e viaggia solo nell'header `apikey`, mai come Bearer. L'accesso è un codice inviato per email (`SupabaseAuth`, GoTrue `/otp` e `/verify`; il codice arriva se i modelli "Magic Link" e "Confirm signup" contengono `{{ .Token }}`. Il piano gratuito di Supabase lascia i modelli predefiniti, che portano solo un link: in quel caso il link si copia dall'email e si incolla al posto del codice, e `verifyCode` ne usa solo l'hash del token, dopo aver controllato che punti a `/auth/v1/verify` del progetto, in HTTPS e per un accesso (`magiclink` o `signup`); il link non viene mai aperto), così non si apre nessun link e funziona uguale su telefono e browser. `SyncAccount` tiene la sessione solo a vault aperto: allo sblocco `VaultGate` la legge dall'impostazione `sync.session`, sigillata con la chiave locale (`VaultKeeper.saveSetting`, tabella `vault_settings`, schema locale v4, dati associati con nome e workspace), la rinnova un minuto prima della scadenza e la risigilla; al blocco la dimentica. Una sessione danneggiata vuol dire accedere di nuovo, mai un vault che non si apre. Senza sessione il token lancia `ServerUnavailableException`, quindi il motore resta offline. `SyncController` sincronizza allo sblocco e all'accesso, 2 s dopo l'ultima modifica salvata, ogni minuto e al ritorno in primo piano (quando le sincronizzazioni non trovano nulla quella periodica rallenta fino a una ogni 5 minuti, e torna a ogni minuto dopo una modifica o una riga nuova), una sincronizzazione alla volta; viene chiuso prima che le chiavi siano rilasciate, e quello che una sincronizzazione in corso fa dopo viene ignorato. Righe nuove ricaricano la libreria (`VaultNoteStore.reload`). Alla prima sincronizzazione il fondatore registra il workspace (idempotente: 409 è un successo) e pubblica il registro dei membri; il cursore `SyncStream.membership` conta quanti record il server ha, e un registro diverso già presente sotto lo stesso workspace è `LedgerRollbackException` (stato "dati non verificati"). Il pulsante cloud nella libreria mostra lo stato e apre il foglio di accesso. **Limite noto:** chi conosce l'id di un workspace e lo registra per primo lo blocca al proprietario.
* **Eliminazione dell'account (2026-10-14, richiesta da Google Play):** nel foglio Sincronizzazione, «Elimina account» chiede conferma e chiama la Edge Function `delete-account` con il token di sessione e il corpo fisso `{"confirm":"delete-account"}` (`SupabaseAuth.deleteAccount`, `SyncAccount.deleteAccount`, `SyncController.deleteAccount`). La funzione non usa la chiave di servizio: chiede al database *come il chiamante* `sole_workspaces()` (i workspace di cui l'account è l'unico), cancella da R2 tutti i blob `<workspace>/` di quei workspace (stesso elenco e stessa firma di `blob-url`; un errore di R2 è un 503 e l'account resta intatto, quindi si può ripetere), poi chiama `delete_account()` e ripulisce R2 una seconda volta per i workspace che il database ha davvero cancellato. `delete_account()` (migrazione `20261014000000_account_deletion.sql`, security definer, solo `authenticated`, sempre e solo `auth.uid()`) in una transazione blocca le righe dei workspace dell'account (un'ammissione in corso aspetta: un workspace a cui si è unito un altro account non viene mai cancellato), cancella i workspace di cui è l'unico account (righe, registro e `KeyBundle` vanno con il `on delete cascade`, i flussi restano append-only per tutti gli altri), lo toglie dagli altri workspace, cancella le sue righe `device_links` e il suo utente in `auth.users`. Un workspace che ha anche altri account tiene righe e blob: sono note anche loro. Le note restano sul dispositivo; il vault scrive l'impostazione sigillata `sync.retired` e da allora non si sincronizza né offre l'accesso (il server ha dimenticato il workspace, mentre i cursori del vault contano ancora quello che vi aveva spinto e letto: un account nuovo non riceverebbe le note). Un'impostazione `sync.retired` danneggiata vale come presente. **Limiti noti:** gli altri dispositivi collegati allo stesso account perdono la sessione e, se qualcuno vi accede con un nuovo account, la loro sincronizzazione viene rifiutata; un blob caricato su R2 dopo la seconda pulizia resta lì, ciphertext che nessuna chiave sul server apre. Test: `supabase/tests/rls_test.sql`, `supabase/functions/delete-account/handler_test.ts`, `supabase_auth_test.dart`, `test/sync/account_deletion_test.dart`.
* **Registrazioni su R2 (2026-10-13):** con un progetto configurato, dopo ogni sincronizzazione riuscita `BlobSync` (`lib/sync/blob_sync.dart`) carica le registrazioni referenziate dalle note che il dispositivo ha e il server non ancora; quali sono già su R2 è un'impostazione sigillata del vault (`sync.blobs-sent`), così nulla parte due volte e un'impostazione danneggiata costa solo un ricaricamento innocuo. Una registrazione di un altro dispositivo si scarica alla prima pressione di play (`NotePlayback` con `ensureLocal`), non prima: meno traffico e nessuna richiesta che riveli quali note si aprono. Nel dominio `BlobReplication` (`blob_storage_media`, port `RemoteBlobStore`) copia solo ciphertext: il download entra nello store locale solo se è lungo esattamente quanto dicono i metadati della nota (`ChunkLayout.ciphertextLengthFor`) e ha il loro digest, un server che manda di più viene fermato a quella soglia, e ogni chunk resta autenticato alla riproduzione. **Digest dei blob (2026-10-18, test di sicurezza):** l'autenticazione dei chunk prova solo che il blob è stato sigillato da chi ha la GroupKey, e la BlobKey si ricava da GroupKey e `SubkeyId` scritto nella nota: un membro che scrive poteva sigillare un'altra registrazione o immagine della stessa lunghezza sotto la stessa chiave, cancellare l'originale su R2 e caricare la sua, mostrata dentro la nota firmata da un altro e invisibile all'autore (il suo dispositivo ha la copia locale). Ora `EncryptedBlobStorage.write` calcola il BLAKE2b-256 del ciphertext (port `ContentHasher`, `SodiumContentHasher`), `SealedBlob.digest` lo porta nella nota firmata (`RecordedNoteCodec` versione 5: flag bit 3, poi per ogni registrazione e immagine `has | digest`, scritta solo se almeno un blob ha il digest) e `BlobReplication` rifiuta un download con un digest diverso prima di salvarlo (`MalformedBlobException`). **Limiti noti:** i blob sigillati prima di questa versione non hanno digest e restano sostituibili; un'app più vecchia vede una nota con registrazioni o immagini nuove come illeggibile; due play contemporanei condividono un download. L'adapter `R2RemoteBlobStore` (`blob_storage_media_adapters/lib/remote_blobs.dart`, su ogni piattaforma) chiede l'URL alla Edge Function `blob-url` con il token di sessione e poi parla direttamente con R2: il token non arriva mai a R2, un URL non HTTPS o con credenziali viene rifiutato, `PUT` con `If-None-Match: *` (412 = già caricato, quindi successo), corpo in streaming con `Content-Length`. Rete, 5xx, 408 e 429 sono `RemoteBlobUnavailableException` (la sincronizzazione resta "offline" e riprova; il player dice di collegarsi), gli altri rifiuti `RemoteBlobRejectedException`. **Cancellazione su R2 (2026-10-14):** il server non sa quali blob servono (non vede le note), quindi decide un dispositivo membro, da un vault appena sincronizzato. `BlobPruning` (`blob_storage_media`, port `RemoteBlobStore.delete`/`list`) cancella i blob *rilasciati*, cioè che una nota ha smesso di citare su questo dispositivo (eliminata per sempre, registrazione o immagine tolta: `VaultNoteStore.onRelease`, impostazione sigillata `sync.blobs-released`), se nessuna nota li ha ripresi; e al più una volta al giorno (l'ora dell'ultima sta nell'impostazione sigillata `sync.blobs-swept`, così sbloccare di nuovo non rielenca il workspace) fa una *pulizia*: elenca il workspace e cancella ogni blob che nessuna nota cita, caricato da più di 24 ore (un dispositivo carica un blob solo dopo che la sua nota è arrivata al server, quindi un blob più vecchio dell'ultimo pull e non citato non appartiene a nessuna nota sincronizzata). La pulizia recupera anche quello che è rimasto su R2 prima di questa funzione o da un dispositivo abbandonato. `BlobSync.prune` gira dopo ogni sincronizzazione riuscita, dopo i caricamenti, ma mai con modifiche ancora in coda (`SyncEngine.hasUnsentWrites`: le note sul server potrebbero ancora citare il blob) né con record che l'app non sa leggere (una nota di un'app più nuova potrebbe citare blob che questa non vede). Un blob cancellato esce anche da `sync.blobs-sent`. La pulizia legge al più 100 pagine e si ferma a un cursore ripetuto; un id elencato che una nota cita non viene mai cancellato. **Limiti noti:** una versione vecchia di una nota scritta offline da un altro dispositivo, che vince il conflitto dopo la cancellazione, cita una registrazione che non c'è più (il player dice che non è disponibile); lo stesso per una nota ripristinata da un backup dopo che il blob è stato cancellato; un membro ostile può cancellare tutti i blob del workspace.
* **Collegamento tra dispositivi (2026-10-13):** telefono e browser della stessa persona condividono un workspace; ogni dispositivo ha la propria identità e la propria passphrase. Dal foglio Sincronizzazione, a vault sincronizzato, «Collega un altro dispositivo» (`LinkDeviceSheet`) genera un `LinkCode` (10 simboli Crockford base 32, 50 bit) e `VaultKeeper.offerLink` pubblica un `LinkOffer`: l'`Invitation` (workspace e fondatore) sigillata con una chiave Argon2id del codice (sale casuale; i costi sono quelli della build, mai letti dal server) e dati associati con l'id del collegamento. Sul nuovo dispositivo, al primo avvio, «Collega a un vault esistente» (`JoinVaultScreen`) chiede l'accesso con la stessa email, il codice e una passphrase; la sessione resta in memoria finché il vault non esiste, poi viene sigillata come `sync.session`. `VaultKeeper.join` apre l'offerta più recente dell'account (altrimenti `LinkCodeRejectedException`), genera l'identità e pubblica un `LinkAnswer` con la sua `PublicIdentity` sotto la stessa chiave (dati associati diversi). `LinkOffering.poll` (ogni 2 s) ignora le risposte che non si aprono e chiama `SyncEngine.admit`: un record `MemberInvited` come owner, pubblicato, e un `KeyBundle` con tutte le epoche (`appendKeyBundle`, ora nel port `SyncServer`); ripetere è innocuo (`grantAll` se è già membro), così un'ammissione interrotta si completa al giro dopo. `LinkRequest.poll` crea il vault solo quando il registro del server si verifica contro il fondatore dell'offerta, il dispositivo è membro e ha la chiave dell'epoca corrente; il suo header è la versione 2, con il proprio `member` (la passkey controlla quello). Il server vede solo l'id del collegamento, le dimensioni e il ciphertext: per far passare un dispositivo suo dovrebbe indovinare il codice nei 10 minuti di validità, al costo di un Argon2id per tentativo. Il foglio tiene aperto il vault (`hold()`) e chiuderlo ritira il codice. Port `DeviceLinkChannel`, implementato da `SupabaseSyncServer` sulla tabella `device_links`. **Limiti noti:** ci si unisce solo da un vault vuoto (un dispositivo nuovo, o «Nuovo vault»); serve lo stesso account Supabase su entrambi; le righe scadute restano nella tabella (invisibili) finché non ci sarà una pulizia lato server; un dispositivo ammesso e poi abbandonato resta membro finché un altro non lo rimuove (vedi «Membri e revoca»).
* **Membri e revoca (2026-10-15):** nel foglio Sincronizzazione, «Membri del vault» (`MembersSheet`, `lib/sync/members_sheet.dart`) elenca i membri del registro nell'ordine di ingresso, con il ruolo e un'impronta (i primi 16 caratteri esadecimali della chiave di firma, in quattro gruppi): i dispositivi non hanno nome, quindi «Questo dispositivo» mostra la propria impronta per confrontarla con l'altro schermo. Un proprietario rimuove un altro dispositivo dopo una conferma (`SyncController.revoke`, nessuna sincronizzazione in parallelo, vault tenuto aperto). `SyncEngine.revoke` vuole il server: pubblica quello che manca, legge il registro più recente, poi `WorkspaceAdministration.revoke` firma `MemberRevoked` e ruota la GroupKey (epoca successiva, concessa solo a chi resta). Record e `KeyBundle` entrano nel registro locale *prima* di partire, e il bundle resta anche nell'impostazione `sync.pending-bundle` (sigillata con la chiave locale) finché il server non lo ha: la chiave nuova esiste solo qui, il vault deve riaprirsi con lei e gli altri non possono scrivere nell'epoca nuova finché non la ricevono; la sincronizzazione successiva, anche dopo un blocco, completa l'invio. Se il server non risponde prima della firma non cambia nulla. **Righe che non fermano la sincronizzazione (2026-10-18, test di sicurezza):** `RevisionAuthenticator` scarta come una riga rifiutata la revisione di chi oggi non scrive *prima* di guardare la posizione del registro che cita, quindi un lettore o un membro rimosso che cita una posizione inesistente o biforcata non ferma più tutti con `LedgerRollbackException`; scarta anche un vettore di versione che nomina chi non è mai stato membro o ha un contatore oltre 2^31 − 1 (prima la modifica locale successiva di quel record andava oltre l'uint32 del formato e il record restava bloccato; `WireWriter` ora rifiuta invece di troncare). Un `KeyBundle` che cita un record del registro non ancora arrivato si rilegge dopo, invece di essere saltato per sempre (la revoca pubblica record e bundle uno dopo l'altro). **Limite noto:** chi scrive oggi e cita una posizione falsa ferma ancora la sincronizzazione con «dati non verificati»: è la prova che serve a scoprire un server che nasconde o biforca il registro; si sblocca rimuovendo quel membro. Un dispositivo rimosso, al primo registro che lo dice, lancia `RemovedFromWorkspaceException` (stato «rimosso» nel foglio Sincronizzazione), non si sincronizza più e non scrive (`NotAuthorizedException`, quindi «Salvataggio non riuscito»); tiene le note che aveva e le chiavi delle epoche vecchie, ma non apre nulla di scritto dopo, e le sue modifiche successive sono scartate dagli altri (`RevisionAuthenticator`). Ci si può rimuovere solo da un altro dispositivo. La rimozione toglie anche l'account del membro dal workspace sul server, se nessun altro membro lo usa (vedi «Inviti tra account»). **Limiti noti:** un proprio dispositivo rimosso usa ancora lo stesso account Supabase, quindi il server non lo esclude (vedi «Compattazione delle revisioni» e la cancellazione su R2 per quello che può ancora fare); due proprietari che cambiano il registro insieme biforcano il registro (`LedgerRollbackException`, come per il collegamento); un dispositivo rimosso non si può ricollegare senza un vault nuovo. Test: `device_linking_test.dart` (gruppo `revocation`), `members_sheet_test.dart`.
* **Inviti tra account (2026-10-15):** un proprietario invita un'altra persona, con il suo account e il suo dispositivo. In «Membri del vault», a vault sincronizzato, «Invita una persona» (`InviteSheet`, `lib/sync/invite_sheet.dart`) fa scegliere il ruolo (Può leggere, Può modificare, Proprietario) e mostra un `InviteCode`: 16 simboli Crockford base 32, i primi 6 sono il `lookup` con cui il server trova l'offerta, gli altri 10 (50 bit) restano segreti. `VaultKeeper.offerInvite` pubblica un `InviteOffer` (l'`Invitation` sigillata con una chiave Argon2id di tutto il codice, dati associati con il `lookup`). La persona, al primo avvio, sceglie «Collega a un vault esistente», accede con la *propria* email e scrive il codice: `JoinVaultScreen` distingue i due codici dalla lunghezza (10 per un proprio dispositivo, 16 per un invito) e `VaultKeeper.acceptInvite` risponde con un `InviteAnswer` che sigilla la sua `PublicIdentity` e l'id del suo account (`AccountId`, l'`auth.uid()` della sessione). `InviteOffering.poll` ammette il dispositivo con il ruolo scelto e, prima del record `MemberInvited`, chiede al server di far entrare l'account che la risposta nomina (`MemberAccounts.admitMember`); poi `LinkRequest.poll` crea il vault come per il collegamento. Lo stesso `CodeAdmissionPanel` (`link_device_sheet.dart`) mostra il codice e aspetta in entrambi i fogli. **Lato server** (migrazione `20261015100000_workspace_invites.sql`): `workspace_invites` contiene offerte e risposte per 15 minuti (stessa quota di `device_links`); `invite_offer(code)` restituisce l'offerta più recente sotto un `lookup`, mai un elenco; le risposte le legge e cancella solo l'account che ha pubblicato l'offerta. `workspace_members` dice con quale account entra ogni membro: la scrive `admit_member(workspace, member, account, manage)` (solo un account che gestisce; un proprietario invitato riceve anche `can_manage`), e `remove_member(workspace, member)` la cancella e toglie l'account da `workspace_accounts` quando nessun altro membro lo usa e non è il chiamante. `SyncEngine.admit` registra così anche i propri dispositivi collegati; `SyncEngine.revoke` chiama `remove_member` dopo aver firmato, e se il server non risponde la rimozione resta nell'impostazione sigillata `sync.pending-removals` finché una sincronizzazione non la completa. Un server senza le funzioni (404) vale come prima per il proprio account; far entrare un altro account invece fallisce. Il server vede il `lookup`, gli id degli account e le chiavi pubbliche dei membri (già nel registro), mai il resto del codice: per far passare un dispositivo suo dovrebbe indovinare 50 bit, un Argon2id per tentativo, in 10 minuti. **Limiti noti:** il codice va dato alla persona per un canale fidato, perché chi lo conosce entra con il ruolo scelto; solo un proprietario invita, quindi chi può modificare o leggere non collega da sé un secondo dispositivo; i membri non hanno nome (si riconoscono dall'impronta); chi può solo leggere vede «Salvataggio non riuscito» se modifica una nota; la persona invitata entra in un vault nuovo, quindi su un dispositivo che ha già un vault aggiunge prima «Nuovo vault» (vedi «Più vault sul dispositivo»); il server può sempre escludere un account (o lasciarlo dentro), come poteva già. Test: `device_linking_test.dart` (gruppo `invites`), `supabase/tests/rls_test.sql`, `supabase_sync_server_test.dart`, `supabase_e2e_test.dart`, `invite_test.dart`.
* **Più vault sul dispositivo (2026-10-15):** un dispositivo tiene fino a 20 vault (`VaultShelf`, `offline_sync`), per esempio le proprie note e il vault che un'altra persona ha condiviso. Ognuno ha il proprio database, le proprie registrazioni e immagini, la propria passphrase, identità, workspace, sessione sigillata e passkey: il primo usa i nomi di sempre (`vault.sqlite`, `blobs`, IndexedDB `modusnote-blobs`), gli altri `vault-<id>.sqlite`, `blobs-<id>` e `modusnote-blobs-<id>` (`vaultStorageNames`), con `id` di 16 cifre esadecimali, quindi un dispositivo con un solo vault non cambia nulla. L'elenco sta in `vaults.sqlite` (`SqliteShelfStore`, accanto ai vault, in IndexedDB sul web): id, nome e un numero (`scope`, da 0 a 19, 0 per il primo) che separa le risorse di sistema; un elenco danneggiato o incoerente vale come il solo primo vault. `VaultShelfGate` (`lib/vault/vault_shelf_gate.dart`) apre un vault alla volta: sulla schermata di sblocco o di creazione il nome del vault apre l'elenco, dove si passa a un altro vault, si rinomina, si aggiunge «Nuovo vault» (poi si crea o si collega come al primo avvio, anche con un invito) e si rimuove il vault corrente se è vuoto e non è il primo (ricontrollato prima di cancellarne il database). Si cambia vault solo a vault bloccato; il database del vault precedente si chiude dopo che la sua schermata è sparita. I promemoria delle password usano id di notifica `scope · 2^24 + id` (`LocalReminderScheduler.scope`) e ogni vault sostituisce solo i propri, quindi il primo tiene gli id di sempre. I nomi sono una riga sicura fino a 40 caratteri (niente caratteri di controllo o bidirezionali); il primo vault, finché non lo si rinomina, si chiama «Il mio vault». **Limiti noti:** i nomi dei vault sono in chiaro sul dispositivo (lo dice l'elenco), come il loro numero; si rimuove solo un vault vuoto, quindi per togliere un vault con note bisogna ancora disinstallare l'app; il limite di 64 notifiche di iOS è condiviso tra i vault. Test: `vault_shelf_test.dart`, `sqlite_shelf_store_test.dart`, `vault_shelf_gate_test.dart`, `vault_storage_names_test.dart`, `local_reminder_scheduler_test.dart`.
* **Limite noto:** Argon2id gira sull'isolate della UI (le `SecureKey` non attraversano gli isolate), quindi lo sblocco blocca l'interfaccia per circa un secondo; la UI mostra prima l'indicatore di avanzamento.
* **Blocco automatico (decisione del 2026-10-11):** `AutoLock` (`lib/vault/auto_lock.dart`) chiude il vault dopo 5 minuti senza tocchi, tasti o modifiche e dopo 30 secondi in background (`hidden`/`paused`). Il background si controlla anche con l'orologio al ritorno, perché un processo congelato dal sistema non esegue timer. Tocchi e tasti si osservano a livello di binding (pointer router globale e `HardwareKeyboard`), la tastiera software tramite l'`onChanged` dell'editor. Mentre il foglio di registrazione è aperto il vault resta aperto (`hold()`), così la chiave non sparisce a metà di una registrazione. Prima di bloccare si chiudono tutte le schermate sopra la libreria, quindi nessuna nota decifrata resta visibile; una modifica non salvata va persa, come la registrazione di una modifica abbandonata.
* **Schermo privato (decisione del 2026-10-12):** su Android `MainActivity` imposta `FLAG_SECURE` prima del primo frame: niente screenshot, registrazioni dello schermo, trasmissione né miniatura tra le app recenti, sempre, anche a vault bloccato. iOS non permette di bloccare gli screenshot: `PrivacyCover` (in `AppDelegate.swift`) copre la finestra con Deep Void quando la scena smette di essere attiva, così il selettore delle app non mostra né fotografa le note. Ascolta le notifiche di `UIScene` invece di sovrascrivere `FlutterSceneDelegate`, che inoltra il ciclo di vita al motore (e quindi ad `AutoLock`). Sul web non esiste un equivalente. `test/platform/screen_privacy_test.dart` controlla i sorgenti nativi. **Backup (2026-10-18):** come Android con `allowBackup="false"`, su iOS `AppDelegate` esclude dai backup iCloud e del computer tutta la cartella Application Support (vault, registrazioni, elenco dei vault): una copia ripristinata firmerebbe come questo dispositivo su un altro telefono, e il backup porterebbe fuori l'identità sigillata (`test/platform/native_privacy_test.dart`).
* **Tipi di nota, icone e colori (decisione del 2026-10-11):** ogni schema può nominare un'icona (`NoteIcon`) e un colore d'accento (`NoteTint`). Sono nomi, non immagini né colori: l'app li traduce in `lib/notes/note_appearance.dart` e un nome sconosciuto (da un'app più nuova) viene ignorato. Canzone: nota musicale, viola. Sogno: luna, rosa. Diario giornaliero: calendario, rosa (la notte e il giorno, le due note personali). To-do: lista con caselle, ciano. Appunto: matita, oro. Documento: pagina, argento (`NoteTint.silver`, Dust Silver: la palette non ha un quinto accento). Libro, capitolo, personaggio e luogo sono una famiglia: tutti oro, ciascuno con la sua icona (libro aperto, segnalibro, persona, segnaposto). Le icone restano uniche per tipo, i colori per famiglia. Filtri e scelta del tipo li mostrano (i filtri della libreria su una sola riga che scorre in orizzontale); ogni colore è testo AA su entrambi gli sfondi (`theme_test`). La card della libreria è tutta colorata (decisione del 2026-10-13): Abyssal Slate velato dal colore del tipo a 1/φ⁴ (`NoteAppearance.wash`), il massimo che tiene in AA testo, data e avanzamento; l'icona resta nel colore pieno, l'etichetta del tipo è Dust Silver (il viola su card viola andrebbe sotto AA). Il titolo mostra solo righe intere e la card si allunga oltre φ : 1 solo quando la dimensione del testo di sistema non lascia spazio a tipo, una riga di titolo e data.
* **To-do come lista (decisione del 2026-10-11):** `task` v2 ha un titolo facoltativo e un campo `ChecklistFieldType` (task di una riga, al massimo 200, 500 caratteri ciascuno, niente caratteri di controllo o bidirezionali). Nell'editor Invio aggiunge un task sotto quello corrente e Invio su un task vuoto lo toglie e chiude la lista; i task vuoti non entrano mai nel valore. Le note `task` v1 si leggono tramite `SeedSchemas.catalog` (`SchemaCatalog` + `SchemaMigration` con `DeriveField`): la descrizione, resa una riga sicura, diventa l'unico task e "completata" il suo stato. La nota viene mostrata come v2 senza toccare revisione e data, e riscritta come v2 solo al salvataggio successivo, così aprire l'app non riscrive le note su ogni dispositivo.
* **Editor delle note (decisione del 2026-10-13, sostituisce le schede Scrivi/Anteprima):** l'editor somiglia a Standard Notes e Notesnook. La pagina è il contenuto: il primo campo di testo dello schema è il titolo grande senza bordo, il primo campo Markdown o testo arricchito (altrimenti la checklist) è il corpo, le registrazioni stanno sempre sopra il corpo, gli altri campi si piegano sotto «Dettagli» (aperti se sono tutti vuoti o se uno ha un errore). Il tipo si sceglie dal menu nel titolo della barra (solo finché la nota non è salvata; il menu è un nodo di semantica a sé con ruolo pulsante, altrimenti sul web finirebbe dentro l'intestazione della pagina). **Salvataggio automatico:** 1 s dopo l'ultima modifica, subito all'uscita e quando l'app va in background, un salvataggio alla volta e con il vault tenuto aperto (`hold()`) mentre scrive; una nota nuova vuota non si salva; con campi obbligatori mancanti lo stato dice «Non salvata» e uscire chiede se scartare. Lo stato (Salvata / Salvataggio… / Non salvata / Salvataggio non riuscito) sta nella barra, «Salvata» solo per una nota che esiste. Il blocco automatico ferma il timer: una modifica non ancora salvata va persa. **Markdown in tempo reale:** il campo resta il sorgente Markdown e lo disegna mentre si scrive (`MarkdownEditingController.buildTextSpan`, `lib/notes/editor/`): marcatori attenuati in Dust Silver, grassetto, corsivo, barrato, codice, titoli, citazioni, elenchi e task spuntati con i colori del tema; nessuna finestra di anteprima separata. `MarkdownSyntax.scan` è nostro, riga per riga e con le ricerche delle chiusure memorizzate, quindi lineare qualunque cosa contenga la nota (fino a 100.000 caratteri). L'HTML resta testo, un link è solo colorato e non si apre, nessuna immagine viene scaricata. La barra di formattazione (`MarkdownToolbar`, sopra la tastiera) e le scorciatoie (Ctrl, o ⌘ su Apple: B, I, E, K, Maiusc+H/X/9/8/7/./-, Ctrl+Alt+C per il blocco di codice perché Ctrl+Maiusc+C apre l'ispettore di Chrome) chiamano gli stessi `MarkdownCommands`, che alternano i marcatori sulla selezione. Invio in un elenco continua l'elenco (numeri +1, task non spuntati) e su una voce vuota lo chiude (`MarkdownListFormatter`, vale con ogni tastiera). Il parser `MarkdownDocument` resta per il testo senza markup delle card (`plainText`); `MarkdownView` non è più usato dall'editor.
* **Tre colonne sugli schermi larghi (decisione del 2026-10-13):** da una finestra larga almeno `Extents.xxxl` (987 dp, `NoteLibraryScreen.wideFrom`), cioè il browser di un computer o un tablet in orizzontale, la libreria mostra tre colonne come un'app di note desktop: «Tutte le note», tipi di nota, l'albero delle categorie (rientrato per livello), cestino e pulsanti del vault, Categorie compreso (`Extents.l`); tipo e categoria si combinano; ricerca, «Nuova nota» e l'elenco delle note (`Extents.xl`); la nota aperta nel resto. Sotto quella larghezza restano le card e le pagine. La scelta dipende solo dalla larghezza, non dalla piattaforma. L'editor accanto all'elenco è lo stesso `NoteEditorScreen` con `onClose` (pulsante Chiudi al posto di Indietro, nessun `PopScope` che blocchi); prima di aprire un'altra nota, il cestino o una nota nuova la libreria chiama `NoteEditorScreenState.settle()`, che salva quello che manca e, se la nota non si può salvare, chiede come all'uscita: «Continua a scrivere» la lascia aperta. Ogni nota aperta ha un `GlobalKey` nuovo, così lo stato di una nota non passa mai a un'altra. Una nota nuova finisce nella categoria aperta quando è stata iniziata (`NoteEditorScreen.category`, letta in `initState`), anche se intanto l'elenco accanto passa a un'altra; una pressione lunga su una riga la sposta, come sulle card. **Selezione multipla:** Ctrl+clic (⌘ su Apple) aggiunge o toglie una nota senza aprirla, Maiusc+clic prende tutte quelle tra l'ultima scelta e questa, il pulsante «Seleziona note» fa scegliere anche con un clic semplice; Esc o la X finiscono. Una barra sopra l'elenco dice quante sono e le sposta insieme nel cestino (con «Annulla») o in una categoria. Si agisce solo sulle note che l'elenco mostra, quindi una nota scelta e poi nascosta da un filtro o dalla ricerca non viene toccata; se tra quelle da cestinare c'è la nota aperta, prima si salva (`settle()`) e si chiude.
* **Temi e atmosfere (2026-10-15):** tre temi per tutta l'app, schermata di sblocco compresa (`AppTheme`, `lib/theme/modus_themes.dart`): **Modus** (il marchio, predefinito), **Riposante** (scuro, niente nero né bianco puri, testo caldo, contrasto del testo tra 7:1 e 15:1 invece di 18,7:1) e **Carta** (chiaro, seppia caldo, per la luce del giorno). Si spegne con «Adatta al tipo di nota». * **Palette dei comandi (decisione del 2026-10-13):** Ctrl+P (⌘P su Apple), o la lente nella colonna di sinistra, apre `CommandPalette` (`lib/notes/command_palette.dart`) su ogni larghezza: si scrive, le frecce scelgono, Invio esegue, Esc chiude. Senza testo vengono prima le note più recenti, con del testo prima i comandi. * **Colonne richiudibili e modalità focus (2026-10-14):** sulle tre colonne il menu laterale e l'elenco delle note si chiudono dal pulsante « nella loro intestazione, con Ctrl+\\ (⌘\\) e Ctrl+Maiusc+\\ (⌘⇧\\) o dalla palette, e lasciano una sola barra stretta (`Spacing.xxl`) con i pulsanti per riaprirli, la palette e «Nuova nota»; l'elenco chiuso resta montato (`Offstage`), quindi tiene scorrimento e selezione. Lo stato vale finché la libreria è aperta, non viene salvato. La **modalità focus** dell'editor (pulsante nella barra, Ctrl+Maiusc+F o ⌘⇧F, anche dalla palette) lascia solo titolo e testo: niente tipo, cestino, dettagli, registrazioni, allegati, barra di formattazione (le scorciatoie restano) né sezioni sotto la nota; i campi nascosti restano montati con il loro stato. Sulle tre colonne chiude anche menu ed elenco (e la barra), che tornano come erano. Esc o Indietro escono dalla modalità prima di lasciare la pagina; aprire un'altra nota ne esce, e così una nota che non si può salvare, perché i campi mancanti si vedano. * **Backup ed esportazione (decisione del 2026-10-13):** sul web il pulsante «Backup ed esportazione» della libreria (`showBackupSheet`, `lib/backup/`) offre tre cose; su mobile manca, perché il port `FileExchange` (salvare e scegliere un file) esiste solo nel browser (`BrowserFileExchange`: download da un blob in memoria, URL revocato subito; scelta con il dialogo del browser, massimo 512 MB). **Backup cifrato:** `VaultKeeper.exportBackup` mette tutti i record vivi (note, cestino compreso, e categorie, opachi come nel vault) in un file `.mnbackup` (`SealedBackup`: `MNBK`, versione, sale, costi Argon2id, busta; sale e costi stanno nei dati associati) sigillato con una frase scelta al momento (due volte, almeno la lunghezza minima della passphrase), mai salvata. Si riapre in qualunque vault, anche di un altro workspace: `openBackup` rifiuta costi fuori soglia prima di Argon2id e ogni altro errore diventa `BackupRejectedException`; `restoreBackup` scrive solo i record che il vault non ha vivi (anche quelli eliminati), così un ripristino non toglie mai una modifica, e dice quanti ne ha aggiunti e quanti c'erano già. **Markdown:** dopo un avviso («Esportare in chiaro?»), un `.zip` (`ZipWriter`, nostro, file non compressi con nomi UTF-8) con un file `.md` per nota fuori dal cestino, in una cartella per categoria: titolo come `#`, corpo così com'è, checklist con le caselle, gli altri campi come righe con etichetta; i nomi sono ripuliti da separatori, caratteri riservati, di controllo e bidirezionali, nomi di dispositivo di Windows, e numerati se ripetuti. Mentre lavora tiene aperto il vault (`hold()`). **Limiti noti:** registrazioni e immagini non entrano in nessuno dei due (i loro blob restano cifrati sul dispositivo e su R2); nel backup le note le citano ancora, e in un altro workspace non si possono riprodurre.
* **Registrazioni nelle note:** il payload cifrato di ogni nota è un `RecordedNote` (`RecordedNoteCodec`): l'entry più i `BlobMetadata` di ogni blob che referenzia, ciascuno con l'epoca della GroupKey da cui deriva la sua BlobKey (la nota viene risigillata alle epoche nuove, il blob no). Un blob referenziato senza metadati, o metadati per un blob non referenziato, rendono la nota illeggibile. `NoteRecorder` registra dal microfono direttamente in un blob sigillato con la GroupKey corrente (`SyncEngine.contentKeyFor`); le registrazioni sostituite, tolte o di una modifica abbandonata vengono cancellate dopo il salvataggio, e i `.enc.part` lasciati da un crash all'avvio.
* **Cestino ed eliminazione (2026-10-13):** eliminare una nota la sposta nel cestino, con «Annulla» nello snackbar; dal cestino (icona nella libreria) si ripristina, si elimina per sempre o si svuota tutto, sempre dopo una conferma. Lo stato «nel cestino» sta dentro il payload cifrato (`RecordedNote.trashedAt`), quindi il server non lo vede e vale su tutti i dispositivi del workspace. `RecordedNoteCodec` scrive la versione 2 (con l'ora, in µs UTC) solo per una nota nel cestino; una nota fuori dal cestino resta la versione 1 byte per byte, e un'app senza cestino vede una nota cestinata come illeggibile, cioè fuori dalla libreria. Una nota nel cestino tiene le sue registrazioni. Eliminare per sempre scrive un `RevisionDeleted` (un tombstone firmato e sigillato, che vince o perde come una modifica, così una copia vecchia non riporta indietro la nota) e cancella i blob locali che nessun'altra nota referenzia; gli altri dispositivi fanno lo stesso quando il tombstone arriva (`VaultNoteStore.reload`), mai per una nota che ha solo smesso di decodificarsi (un'app più nuova potrebbe averla riscritta). Salvare una modifica la toglie dal cestino. Bloccare il vault chiude gli snackbar, così nessun «Annulla» scrive con chiavi rilasciate. Dopo la sincronizzazione successiva i blob eliminati spariscono anche da R2 (vedi "Registrazioni su R2"). **Limite noto:** il cestino non si svuota da solo.
* **Categorie (2026-10-13):** un albero di categorie e sotto-categorie (`NoteCategory`: nome di una riga fino a 80 caratteri senza caratteri di controllo o bidirezionali, genitore, `NoteIcon` e `NoteTint` facoltativi) fino a `CategoryTree.maxDepth` (4) livelli. Ogni categoria è un record cifrato del `SyncEngine` (`CategoryCodec`, primo byte `0x43`, che nessuna versione delle note usa; l'id interno deve coincidere con quello del record), quindi si sincronizza come una nota e il server non vede nomi, struttura né appartenenze. Ogni nota sta in al massimo una categoria, scritta dentro il suo payload cifrato (`RecordedNote.category`, `RecordedNoteCodec` versione 3 con flag; una nota senza categoria resta versione 1 o 2 byte per byte, e un'app più vecchia vede una nota in categoria come illeggibile). Due dispositivi che modificano l'albero insieme possono produrre un genitore sparito, un ciclo o una catena troppo profonda: `CategoryTree` li ripara in lettura nello stesso modo ovunque (radice; ciclo tagliato all'id minore; appeso all'antenato più profondo con spazio), senza riscrivere i record, e con cicli non ricorsivi, perché un membro ostile può scrivere una catena lunga quanto vuole. Ogni dispositivo rifiuta in scrittura cicli e livelli oltre il limite. Eliminare una categoria non elimina nulla: note e sotto-categorie salgono al genitore, poi la categoria diventa un `RevisionDeleted`. Nella libreria il percorso ("Tutte le note › Romanzi › Gialli") e le categorie interne filtrano le note (una categoria mostra anche quelle delle sue sotto-categorie), una nota nuova nasce nella categoria aperta, una pressione lunga sulla card la sposta; `CategoriesScreen` crea, modifica, sposta ed elimina. **Limiti noti:** una nota archiviata su un dispositivo in una categoria che un altro sta eliminando resta senza categoria; il numero e la dimensione dei record restano visibili al server, quindi il numero di categorie si può stimare.
* **Collegamenti tra note (2026-10-13):** un collegamento è un link Markdown `[testo](note:<id della nota>)` (`NoteLinks`, `schema_dynamic_content`): punta all'id, non al titolo, quindi rinominare una nota non rompe i collegamenti, e resta dentro il testo cifrato. Il pulsante «Collega una nota» della barra di formattazione apre la ricerca tra le note e inserisce il link al posto della selezione (o con il titolo della nota); `NoteLinks.markdown` rende il testo una riga sicura senza parentesi quadre. Sotto la nota l'editor mostra «Collegamenti» (le note a cui punta, nell'ordine del testo) e «Citata in» (le note che puntano a lei); un tocco salva la nota corrente e apre l'altra sopra. Un collegamento a una nota eliminata o nel cestino resta visibile, grigio, come «Nota non disponibile». Un link `note:` non apre mai nulla fuori dall'app e non genera richieste di rete; le card mostrano solo il testo del link.
* **Allegati e tipo Documento (2026-10-13):** il tipo `document` (titolo, testo Markdown, allegati, tag) è la pagina di un manuale o di qualunque documento fatto di pagine collegate (vedi "Collegamenti tra note"); in `SeedSchemas.all` sta prima dell'appunto, che resta l'ultimo e quindi il tipo di una nota nuova. Gli allegati sono un campo `AttachmentsFieldType` (al massimo 34, valore `AttachmentsValue`) con due tipi di `Attachment`, entrambi con un testo di una riga sicura fino a 200 caratteri, cercato come il resto della nota: `ImageAttachment` (un blob cifrato e la didascalia; la stessa immagine non compare due volte) e `WebLink` (indirizzo e titolo). **Link:** solo `http` e `https`, senza credenziali, in ASCII stampabile (niente `javascript:`, `file:`, `intent:`, `note:` e niente lettere di altri alfabeti nell'host, così l'indirizzo mostrato è quello aperto), fino a 2048 caratteri; senza schema si intende `https`. L'app non li scarica mai (niente anteprime, icone o titoli): la riga mostra titolo e sito, un tocco mostra l'indirizzo intero e chiede conferma, poi `url_launcher` lo apre nel browser (sul web una scheda nuova con `noopener,noreferrer`). **Immagini:** PNG, JPEG, GIF o WebP fino a 32 MB, 20 000 px per lato e 50 megapixel; `ImageProbe` legge solo l'intestazione e rifiuta tutto il resto (SVG compreso) prima di sigillare, così nessuna bomba di decompressione arriva a un decoder. `ImageStorage` sigilla l'immagine in un blob come le registrazioni (stessa BlobKey per blob, stessa GroupKey corrente, stesso store, stessa replica su R2 con `BlobSync`, che ora carica ogni `KeyedBlob`) e la riapre in memoria: i byte decifrati devono avere formato e dimensioni scritti nei metadati, altrimenti `MalformedBlobException`. I metadati (`ImageMetadata`: formato, larghezza, altezza, ora) stanno nel payload cifrato: `RecordedNoteCodec` versione 4 (flag bit 2 sempre presente, poi le immagini dopo la categoria), scritta solo per una nota con immagini; le altre restano byte per byte nelle versioni 1, 2 o 3, e un'app più vecchia vede una pagina con immagini come illeggibile. Un'immagine di un altro dispositivo si scarica alla prima apertura della pagina; le miniature (φ : 1) si decodificano alla dimensione disegnata (`cacheWidth`), un tocco apre l'immagine a tutto schermo con lo zoom. La scelta passa dal port `ImageChooser`: su telefono `image_picker` (photo picker di Android e PHPicker di iOS, senza permessi), che consegna una copia nella cache dell'app subito cancellata dopo la lettura, sul web un `<input type="file">` letto in memoria (niente URL di oggetto). I byte scelti vengono azzerati dopo la sigillatura. Su iOS `Info.plist` dichiara `NSPhotoLibraryUsageDescription` e `NSCameraUsageDescription` (localizzate) perché App Store le richiede a chi include `image_picker`; su Android `<queries>` dichiara i browser. **Limiti noti:** i metadati EXIF (posizione GPS compresa) restano dentro l'immagine cifrata, visibili ai membri del workspace; una pagina aperta tiene in memoria i file decifrati delle sue immagini, quindi una pagina con decine di foto grandi pesa sulla memoria, e sul web un'immagine da 50 megapixel può chiederne circa 200 MB per decodificarla; PDF e altri file non si allegano, perché aprirli in un'altra app vorrebbe dire un file in chiaro sul disco.
* **Immagini nel testo (2026-10-14):** un'immagine può stare nel flusso del testo Markdown, dove la si scrive, oltre che tra gli allegati. Nel testo è un'immagine Markdown con lo schema `image:` e l'id del blob, `![didascalia](image:<id>)` (`InlineImages`, `schema_dynamic_content`: didascalia di una riga sicura fino a 200 unità UTF-16, senza parentesi quadre, caratteri di controllo o bidirezionali, mai tagliata a metà di un carattere; ricerca lineare). Un'immagine Markdown con qualunque altro indirizzo resta testo e non si scarica mai. Le immagini di una nota sono quelle allegate più quelle nel testo (`InlineImages.picturesOf`, usata da `RecordedNote`), quindi metadati, sigillatura, replica su R2, download alla prima apertura e cancellazione restano quelli degli allegati e il formato del payload non cambia (versione 4 se ci sono immagini). Un'app più vecchia vede una nota con immagini nel testo come illeggibile. Nell'editor «Inserisci immagine» della barra di formattazione sceglie e sigilla l'immagine (`MarkdownCommands.image`, su una riga sua; la selezione di una riga diventa la didascalia). `MarkdownEditingController` la disegna dentro il campo (`InlinePicture`, `lib/notes/editor/`): il `!` diventa un `WidgetSpan` con l'immagine e gli altri caratteri del riferimento segnaposti vuoti, così il testo, gli offset e ciò che si salva restano il sorgente. Mettendo il cursore dentro il riferimento, a campo attivo, ricompare il Markdown per modificare la didascalia. Larghezza al più quella del testo e mai oltre i pixel dell'immagine, altezza al più `Extents.xxl`, misure dai metadati (il testo non salta), decodifica alla dimensione disegnata; un tocco la apre a tutto schermo (`ImageViewer`). Se ne disegnano al più 34 per testo (`MarkdownEditingController.maxPictures`), le altre restano Markdown. Copiare il riferimento in un'altra nota la condivide: il salvataggio prende i metadati dalla nota che la ha (`NoteStore.imageOf`) e `VaultNoteStore.save` non cancella né rilascia un blob che un'altra nota cita ancora. Un riferimento che il vault non conosce mostra «Immagine non disponibile» e la nota non si salva. Le card mostrano la didascalia, l'esportazione Markdown scrive _immagine: didascalia_. **Limiti noti:** un riferimento dentro un blocco di codice conta comunque come immagine; una nota scritta prima di questa versione che contenesse per caso un riferimento `image:` valido diventa illeggibile.
* **Indice dei documenti (2026-10-13):** un manuale è una categoria: le pagine `document` archiviate nella categoria di una pagina e in quelle interne formano l'indice che l'editor mostra sotto la pagina (`PageIndex`, `lib/notes/documents/`). C'è una sezione per categoria, nell'ordine dell'albero e rientrata per livello; le categorie interne senza pagine non compaiono. Le pagine sono in ordine di titolo, con i numeri confrontati per valore («2. Uso» prima di «10. Note», `PageIndex.naturalCompare`, in una passata e senza interi grandi). La pagina aperta è evidenziata, un tocco salva e apre un'altra pagina sopra, «Nuova pagina» la crea nella stessa categoria. Una pagina senza categoria lo dice. Come per i libri, categoria e tipo stanno nei payload cifrati, quindi il server non vede la struttura del manuale. I riferimenti tra le pagine restano i collegamenti `note:`.
* **Libri (2026-10-13):** quattro tipi per scrivere un libro: `book` (titolo, sinossi Markdown, genere, obiettivo di parole, allegati, tag), `book_chapter` (titolo, testo, numero, stato: idea, bozza, rivisto, definitivo; allegati), `book_character` (nome, profilo Markdown, ruolo: protagonista, antagonista, comprimario, secondario; età, obiettivo, conflitto, arco narrativo; allegati) e `book_place` (nome, descrizione, tipo di luogo, epoca; allegati). Il libro è la categoria: capitoli, personaggi e luoghi archiviati nella categoria del libro o in quelle interne sono le sue parti (`BookOutline`, `lib/notes/books/`, riconosciute dal nome del tipo, quindi anche in una versione futura), e il server non ne vede nulla perché categoria e tipo stanno nei payload cifrati. Sotto il libro l'editor mostra le parole scritte nei capitoli rispetto all'obiettivo, con la barra di avanzamento, poi i capitoli per numero (quelli senza numero in fondo) con stato e parole, i personaggi e i luoghi per nome; un tocco salva il libro e apre la parte sopra, «Nuovo capitolo», «Nuovo personaggio» e «Nuovo luogo» la creano già nella categoria del libro. Un libro senza categoria lo dice. Il capitolo conta le parole mentre si scrive. `WordCount` conta le sequenze tra spazi che contengono una lettera o una cifra (i marcatori Markdown da soli non sono parole), in una sola passata. **Limite noto:** un libro raccoglie tutto il sottoalbero della sua categoria, quindi un altro libro in una categoria interna finisce tra le sue parti.
* **Credenziali (2026-10-14):** il tipo `credential` (descrizione, nome utente, password, link, scadenza password; icona chiave, ciano) è l'unico senza corpo, quindi l'editor mostra tutti i campi senza piegarli sotto «Dettagli». La password è un `SecretValue` (tipo `secret` nel documento dell'entry, campo `PasswordFieldType`, al massimo 1024 caratteri, niente caratteri di controllo o bidirezionali): cifrata con la nota come tutto il resto, ma mai cercata (`EntrySearch`), mostrata sulle card né scritta nell'esportazione Markdown (resta nel backup cifrato). Nell'editor è mascherata, senza suggerimenti, correzione automatica, apprendimento della tastiera né autofill; «Mostra» la rivela, «Copia» la copia senza mostrarla e `SecretClipboard` svuota gli appunti dopo 30 s se contengono ancora quella password (su Android e iOS la copia passa dal canale `run.serv.modus/clipboard`: Android la segna sensibile, quindi l'anteprima di sistema mostra puntini e le tastiere non la mettono nella cronologia; iOS la tiene solo sul dispositivo, niente Appunti universali, con scadenza a 30 s anche se l'app viene chiusa) (sul web li svuota comunque, perché leggerli chiederebbe un permesso). Il link è un `UrlFieldType`: lo stesso `WebLink.parse` degli allegati (http/https, ASCII, niente credenziali; senza schema diventa `https://`), si apre solo dal suo pulsante dopo la conferma. **Generatore:** `PasswordGenerator` (dominio) con una `PasswordRecipe`: lunghezza fino a 128 (20 di partenza), lettere minuscole, maiuscole e cifre sempre, e i simboli ASCII che l'utente non esclude; almeno un carattere per classe, poi Fisher–Yates, sempre con `Random.secure`. Ogni ricetta costruibile ha almeno 80 bit di entropia contati per difetto (un carattere per classe, gli altri dall'alfabeto intero), quindi escludere simboli alza la lunghezza minima (`minLengthFor`: 14 con tutti i simboli, 15 senza). **Scadenza:** `PasswordExpiry` calcola i promemoria (7 giorni prima, il giorno prima, il giorno stesso) e li raggruppa per giorno e tipo (`ReminderSlot`, id stabile da giorno e tipo, al più 57 perché iOS ne tiene 64 e 7 sono del diario). `PasswordReminders` (`lib/reminders/`) li ripianifica a ogni modifica delle note a vault aperto, alle 9 del mattino locali, chiede il permesso solo quando c'è qualcosa da ricordare e lascia al sistema quelli già pianificati quando il vault si chiude. Su Android e iOS sono notifiche locali (`flutter_local_notifications`, `LocalReminderScheduler`, orari in UTC calcolati dal fuso del dispositivo; Android senza allarmi esatti, ricevitori per il riavvio, desugaring). Il testo è generico («Una password scade domani», o «2 password…»): mai la descrizione, perché la notifica si vede a schermo bloccato. Sul web non ci sono notifiche (senza service worker il browser non le programma a pagina chiusa): la card della credenziale, come su ogni piattaforma, dice al posto della data «La password scade tra N giorni», «domani», «oggi» o «Password scaduta» da una settimana prima. **Limiti noti:** il sistema conserva fuori dal vault, in chiaro, l'orario di ogni promemoria, cioè le date di scadenza (non a quale nota appartengono); un promemoria arriva solo se il vault è stato aperto dopo l'ultima modifica della scadenza su un altro dispositivo; un'app più vecchia vede una credenziale come illeggibile.
* **Diario giornaliero (2026-10-15):** il tipo `journal` (titolo facoltativo, giorno obbligatorio, pagina Markdown, umore tra ottimo, buono, neutro, giù e difficile, registrazione, allegati, tag; atmosfera Immaginazione) è una pagina per giorno. `Journal` (dominio, `schema_dynamic_content`) riconosce le pagine dal nome del tipo e calcola tutto il resto in memoria, senza indici né richieste al server: giorno e umore stanno nel payload cifrato. Una pagina nuova nasce con il giorno di oggi, o con quello scelto dal calendario (`NoteEditorScreen.day`), mostrato per esteso sopra il titolo; una pagina nuova che contiene solo il giorno non si salva. Senza titolo la pagina si chiama col suo giorno («giovedì 15 ottobre 2026» sullo schermo, `2026-10-15` nei nomi dei file, `NoteTitle.of`). Sotto la pagina: le parole (lo stesso `WordCount` dei capitoli) e «Un anno fa oggi», le pagine dello stesso giorno negli anni precedenti (un 29 febbraio guarda il 28 negli anni senza), con prima riga e umore. Due dispositivi offline possono scrivere due pagine dello stesso giorno: restano entrambe, e «Diario di oggi» (palette e pulsante del calendario) apre quella modificata per ultima, o ne crea una. Filtrando il diario la libreria ordina le pagine per giorno, non per ultima modifica, e mostra il calendario (`JournalCalendar`): il mese in sette colonne di giorni quadrati sugli schermi larghi, la settimana di oggi sul telefono; un punto rosa per ogni giorno scritto, pieno per «ottimo» o senza umore e diviso per φ a ogni umore più basso fino a 1/φ⁴; un tocco apre il giorno o lo crea, i giorni a venire non si toccano; «Non hai ancora scritto oggi» finché oggi non ha una pagina. **Promemoria quotidiano:** spento finché non lo si accende dal pulsante con la campanella del calendario (solo dove ci sono notifiche: Android e iOS), all'ora scelta (21:00 proposte), impostazione sigillata per dispositivo (`journal.reminder`, `JournalReminder`). Invece di una notifica che si ripete, che non saprebbe saltare i giorni scritti, `PasswordReminders` pianifica insieme alle scadenze una notifica per ciascuno dei prossimi 7 giorni senza pagina (`Journal.reminders`, id `Journal.reminderId` che non coincidono mai con quelli delle password) e la ripianifica a ogni sblocco e modifica, su un canale Android a sé. Il testo è generico («È il momento di scrivere nel diario.»). Se il vault non si apre per una settimana i promemoria finiscono, ed è voluto. **Limiti noti:** il sistema conserva in chiaro, fuori dal vault, gli orari dei promemoria e quindi quali dei prossimi giorni non hanno ancora una pagina; un'app più vecchia vede le pagine del diario come illeggibili.
* **Riproduzione (decisione del 2026-10-11):** `RecordingPlayback` decifra il blob con la GroupKey della sua epoca (ogni chunk è autenticato prima che il decoder lo veda) e lo decodifica tutto in memoria: Ogg Opus con la nostra libopus (`OpusAudioDecoder`, su un isolate a parte), WAV PCM16 del web con `WavAudioDecoder`. Il demuxer Ogg accetta solo ciò che scrive il nostro muxer (un flusso logico, CRC, sequenza, nessun pacchetto spezzato tra pagine, OpusHead mono/stereo, famiglia 0, guadagno 0) e rifiuta tutto il resto come `MalformedBlobException`. La riproduzione è limitata a 30 minuti (`DecodedAudio.maxDuration`), controllati sul granule prima di decodificare, e a 48 kHz (`maxSampleRate`, quella di ogni registratore dell'app: a 192 kHz lo stesso limite chiedeva quattro volte la memoria). Il lettore dei chunk unisce i pezzi ricevuti solo quando un frame è completo, così uno store che restituisce pezzi minuscoli non costa una copia per byte. Il PCM diventa un WAV in memoria passato a **flutter_soloud** (versione fissata, `LoadMode.disk` per non espandere a float) dietro il port `RecordingPlayer` dell'app: nessun file in chiaro, nessun socket. Nel pubspec radice `hooks.user_defines.flutter_soloud.no_xiph_libs: true`, altrimenti il build hook scaricherebbe librerie Xiph precompilate senza hash fissato. Niente si decifra finché l'utente non preme play, e i campioni si liberano quando il campo esce dallo schermo. Sul web flutter_soloud porta con sé i suoi `.wasm` precompilati ma non vengono caricati (servono gli script in `index.html`): il player web è Web Audio (vedi "Audio nel browser").
