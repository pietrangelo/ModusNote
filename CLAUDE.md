# ModusNote

## MISSION
Costruire un'applicazione mobile e web offline-first e crittografata end-to-end (E2EE) con motore a tipi dinamici (schemi estensibili per canzoni, sogni, to-do, note libere) e gestione di blob audio cifrati, sincronizzabile in gruppi a zero-knowledge.

- **Stack:** Flutter (Dart 3.13+), pub workspace. Un'unica app per Android, iOS e **web** (Flutter Web, WebAssembly), che riusa gli stessi pacchetti di dominio.
- **Dominio dell'app:** `modus.serv.run`. Identificativo Android/iOS: `run.serv.modus`.
- **Lingue:** l'app è multi-lingua fin dal primo commit (italiano e inglese per iniziare).

## 0. STRUTTURA DEL REPOSITORY E COMANDI

```text
apps/modusnote/                      Shell Flutter (Android, iOS, web): UI, l10n, wiring degli adapter. Nessuna logica di dominio.
packages/identity_cryptography/      Bounded context (dominio puro)
packages/schema_dynamic_content/     Bounded context (dominio puro)
packages/blob_storage_media/         Bounded context (dominio puro)
packages/collaboration_access_control/ Bounded context (dominio puro)
packages/offline_sync/               Bounded context (dominio puro): revisioni firmate, conflitti, coda offline
packages/identity_cryptography_adapters/ Adapter libsodium (pacchetto `sodium`, variante sumo per Argon2id); passkey WebAuthn con PRF sul web (`web_passkeys.dart`)
packages/blob_storage_media_adapters/  Storage dei blob cifrati (filesystem tramite `package:file`), muxer Ogg Opus, encoder libopus (FFI + build hook)
packages/blob_storage_media_recorder_adapters/ Microfono tramite il plugin `record` (pacchetto Flutter, test con `flutter test`)
packages/offline_sync_adapters/      Database locale SQLite (stessa API nativa e WASM): solo buste cifrate; `SupabaseSyncServer` (PostgREST via `package:http`)
packages/<context>_adapters/         Altri petali esterni, creati quando servono
tool/architecture_guard/             Verifica statica delle regole della rosetta
```

Ogni pacchetto di dominio ha la stessa forma:

```text
lib/<context>.dart        API pubblica: l'unico file che altri pacchetti possono importare
lib/src/core/             Entities e Value Object immutabili. Solo dart:core/typed_data/collection/math/convert e package:meta.
lib/src/application/      Use Case e Port. Può usare core e dart:async, nient'altro.
```

Gli adapter **non** vivono in `lib/src/adapters/` del pacchetto di dominio: vanno in un pacchetto separato `<context>_adapters`, così le dipendenze di framework non possono entrare nel dominio nemmeno per sbaglio. `tool/architecture_guard` fa fallire la CI se:
- `core` importa qualcosa al di fuori di `core` e delle librerie consentite;
- `application` importa framework, I/O o pacchetti di terze parti;
- un pacchetto di dominio dichiara dipendenze diverse da `meta` o da altri pacchetti di dominio;
- un pacchetto importa i file `src/` di un altro pacchetto.

`core` e `application` possono importare l'API pubblica (`lib/<context>.dart`) di un altro pacchetto di dominio dichiarato in `dependencies`, mai quella di un pacchetto `_adapters`.

Comandi (dalla radice):

```bash

dart analyze --fatal-infos                        # zero warning ammessi
dart run tool/architecture_guard/bin/architecture_guard.dart
(cd packages/<context> && dart test)              # test di un bounded context
(cd tool/architecture_guard && dart test)
```

### Localizzazione
- Le stringhe dell'app vivono in `apps/modusnote/lib/l10n/app_<lingua>.arb` (template `app_en.arb`). Nessuna stringa visibile all'utente scritta a mano nei widget.
- Il dominio non contiene testo localizzato. Gli schemi seed referenziano le etichette dei campi tramite **chiavi** (es. `schema.song_sketch.field.bpm`), che la UI risolve con `AppLocalizations`. Gli schemi creati dall'utente portano l'etichetta scritta dall'utente così com'è.
- Una nuova lingua si aggiunge con un nuovo file ARB e, su iOS, una voce in `CFBundleLocalizations` di `ios/Runner/Info.plist`.

### Client web
Il client web è un'alternativa completa all'app mobile e si sincronizza con essa: per il protocollo di sync è semplicemente un altro dispositivo del vault, con la propria coppia di chiavi di identità. Si compila con `flutter build web --wasm --csp --no-web-resources-cdn` seguito da `dart run tool/finalize_web_build.dart` (da `apps/modusnote`) (nessuna risorsa caricata da CDN di terzi: CanvasKit e font fanno parte del bundle servito da Cloudflare Pages).

Nel browser alcune garanzie cambiano, e il codice deve tenerne conto in modo esplicito:
* **Memoria delle chiavi:** non esistono `sodium_malloc`/`mlock`. Su web `SecureKey` è un buffer JS che viene azzerato al `dispose()`, ma il motore JS può averne fatto copie. La regola "dispose il prima possibile" resta, ma la garanzia è più debole che su mobile.
* **Fiducia nel codice:** il server che distribuisce l'app web potrebbe servire codice malevolo a ogni caricamento. Mitigazioni obbligatorie: Content-Security-Policy restrittiva (niente script inline o di terze parti, solo `wasm-unsafe-eval`), Subresource Integrity, nessuna dipendenza da CDN, hash delle build pubblicati.
* **XSS ed estensioni:** qualunque script iniettato vede le chiavi in memoria. Niente HTML generato da contenuti utente (Markdown e testo arricchito sono renderizzati come widget, mai come HTML).
* **Persistenza:** niente SQLCipher. Il database locale è SQLite WASM su OPFS/IndexedDB e contiene solo record già cifrati con le buste del dominio. Le chiavi non si salvano mai in `localStorage`/IndexedDB in chiaro.
* **Sblocco:** niente biometria nativa. Il vault si apre con la passphrase oppure con una passkey (WebAuthn con estensione PRF), dove disponibile: vedi "Passkey nel browser".
* **Passkey nel browser (Fase 7.4, 2026-10-13):** a vault aperto il pulsante con l'impronta nella libreria registra una passkey (`WebAuthnPasskeyPrf` in `identity_cryptography_adapters/lib/web_passkeys.dart`, port `PasskeyPrf`): relying party = dominio della pagina, `userVerification: 'required'` sempre (CTAP2 `hmac-secret` ha un segreto separato per l'uso verificato), user handle casuale, nessuna attestazione né server. L'uscita PRF sul `PrfSalt` casuale entra subito in una chiave libsodium e il buffer del browser viene azzerato. Non serve la MasterKey: `VaultKeeper.enrollPasskey` sigilla di nuovo l'identità sotto una sottochiave della PRF (`crypto_kdf`, contesto `mn-passk`) e la chiave locale con `KeyEncapsulation` verso l'identità stessa, in un `PasskeySlot` (tabella `vault_passkey`, schema locale v3) i cui dati associati legano id della passkey, salt, `SubkeyId` e tutti i campi in chiaro del `VaultHeader`; l'identità aperta deve essere il fondatore dell'header. Uno slot copiato da un altro vault, un header modificato o un'altra passkey danno `PasskeyRejectedException`. Una sola passkey per dispositivo: registrarne un'altra o disattivarla chiede al gestore di dimenticare la vecchia (`signalUnknownCredential`, se c'è). La passphrase resta sempre valida. Dove `getClientCapabilities` esclude la PRF il pulsante non compare; se la passkey scelta non ha PRF l'app lo dice. Su mobile il port non c'è (`passkeys: null`).
* **Crypto:** libsodium arriva via WebAssembly (backend JS del pacchetto `sodium`, variante sumo per Argon2id). Non si usa WebCrypto, che non offre XChaCha20-Poly1305 né Argon2id.
* **Vault nel browser (Fase 7.1, 2026-10-12):** `lib/bootstrap/home_web.dart` costruisce lo stesso `VaultKeeper` del mobile (`vault_wiring.dart`, Argon2id `moderate`, circa 1,5 s in Chromium). `web/sodium.js` (libsodium.js sumo, SHA-512 verificato dal pacchetto `sodium`) e `web/sqlite3.wasm` (SHA-256 fissato) sono committati e serviti dalla nostra origine; si aggiornano solo con `apps/modusnote/tool/fetch_web_assets.sh` quando cambiano le versioni dei pacchetti, e `test/platform/web_assets_test.dart` fallisce se non corrispondono. Il database è `/vault.sqlite` su `IndexedDbFileSystem` (OPFS sincrono esiste solo nei worker); le scritture arrivano a IndexedDB in background e vengono forzate quando la scheda si nasconde.
* **Audio nel browser (Fase 7.3, 2026-10-12):** i blob cifrati stanno in un secondo database IndexedDB, `modusnote-blobs` (`IndexedDbCiphertextBlobStore` in `blob_storage_media_adapters/lib/web_media.dart`): un pezzo per `[id, indice]` e uno stato per blob ("in scrittura" o numero di pezzi), quindi il commit è una sola scrittura e le registrazioni interrotte da una scheda chiusa si scartano all'avvio. IndexedDB clona un typed array con tutto il suo buffer, per cui una vista viene sempre copiata prima di salvarla. Il microfono passa dal worklet di `record` (PCM, nessun file); `WebCodecsOpusEncoder` comprime in Opus con l'`AudioEncoder` del browser e il nostro `OggOpusMuxer` (pre-skip dall'OpusHead del browser), quindi una registrazione web è lo stesso Ogg Opus dei telefoni. Dove WebCodecs manca si registra in WAV. `WebCodecsOpusDecoder` riproduce sia le registrazioni web sia quelle dei telefoni (prova con un file libopus fisso nei test), dopo il nostro demuxer. `WebAudioRecordingPlayer` (`lib/audio/web_audio_player.dart`) tiene i campioni in PCM16 e programma segmenti di 5 s di Web Audio: niente URL, elementi `<audio>` o file. I binding WebCodecs sono nostri (`webcodecs.dart`), perché `package:web` 1.1 ha solo la parte video; i buffer che il browser deve riempire si allocano in JS, perché sotto WebAssembly `toJS` su una lista Dart ne passa una copia. Test in Chrome con dart2js e dart2wasm (`test/web`); la prova end-to-end registra dal microfono finto di Chrome, ricarica, riproduce e verifica che nessun blob contenga `OggS`, `OpusHead` o `RIFF` in chiaro.
* **CSP e integrità (Fase 7.2, 2026-10-12):** `web/_headers` vieta tutto tranne la nostra origine: `script-src 'self' 'wasm-unsafe-eval'`, niente `unsafe-inline`/`unsafe-eval`, stili inline solo per hash (i `<style>` che il motore Flutter inserisce: cambiano con le versioni di Flutter e la prova end-to-end lo segnala; più lo `<style>` vuoto che `SelectionArea` dell'anteprima Markdown crea e poi riempie via CSSOM, senza il quale l'anteprima non si disegna), `connect-src 'self'` (l'URL di Supabase si aggiungerà con il deploy), isolamento cross-origin (COOP/COEP/CORP), `frame-ancestors 'none'`. Trusted Types obbligatori: `flutter-js` è la policy di Flutter, `default` è `web/trusted_types.js`, caricato per primo, che concede URL di script solo della nostra origine o dei suoi blob (il caricatore dei worker di skwasm non usa una policy propria) e rifiuta sempre HTML e script da stringhe. Niente service worker (`web/flutter_bootstrap.js`). `tool/finalize_web_build.dart` aggiunge SRI (sha384) agli script di `index.html`, rifiuta script inline o di altre origini e scrive `SHA256SUMS` di tutto il bundle; la CI lo pubblica nel riepilogo del job e carica il bundle come artifact. `tool/web_e2e` (Playwright, versione e lockfile fissati, Chrome di sistema) serve la build con i suoi header su `localhost` (WebAuthn rifiuta gli indirizzi IP come relying party) e, sia per la build WebAssembly sia per quella JavaScript, crea il vault, salva una nota, ricarica, prova una passphrase sbagliata e quella giusta, attiva una passkey sull'autenticatore virtuale di Chrome (CDP `WebAuthn`, con PRF) e riapre il vault con quella, e verifica zero violazioni CSP, zero errori, nessuna richiesta fuori dall'origine e solo ciphertext in IndexedDB. Test: `web_headers_test.dart`, `web_build_test.dart`.
* **Interi a 64 bit (2026-10-12):** la build web ricade su dart2js nei browser senza WasmGC, dove `ByteData.setInt64`/`getInt64` non esistono e gli interi sono esatti solo fino a 2^53. I formati binari del dominio scrivono quindi gli interi a 8 byte con `setPortableInt64`/`getPortableInt64` (`portable_int64.dart`, due metà da 32 bit, stessi byte di `setInt64`) e rifiutano valori oltre ±(2^53 − 1), così ogni piattaforma legge lo stesso numero o rifiuta l'input. Mai usare le funzioni Int64 di `ByteData` nel codice che gira sul web (le helper accettano anche `Endian.little`, usato per i granule Ogg); i test `portable_int64_test.dart` e quelli del muxer e demuxer Ogg girano anche in Chrome in CI.

### Codice per piattaforma (mobile e web)
Il dominio non sa su quale piattaforma gira. Le differenze tra Dart nativo (VM/AOT, `dart:io`, `dart:ffi`) e web (JS/WASM, `dart:js_interop`) restano negli adapter:
* **Ports & Adapters + conditional imports.** Quando un adapter ha bisogno di API diverse per piattaforma, il pacchetto `<context>_adapters` espone una factory che sceglie l'implementazione con `import 'x_stub.dart' if (dart.library.io) 'x_native.dart' if (dart.library.js_interop) 'x_web.dart';`. Lo stub lancia `UnsupportedError`. Nei pacchetti di dominio i conditional imports sono vietati (regola `conditionalImport` dell'architecture guard).
* **libsodium.** L'app usa direttamente il pacchetto `sodium` 4, che compila libsodium con il proprio build hook su Android, iOS e desktop (Flutter esegue gli hook da solo); sul web arriverà `sodium.js` sumo con `dart run sodium:update_web --sumo` (Fase 7). `sodium_libs` non serve più. Gli adapter ricevono l'istanza `SodiumSumo` già inizializzata nel costruttore. L'inizializzazione (asincrona sul web, per caricare il WASM) avviene una sola volta all'avvio dell'app in `lib/bootstrap/`, quindi non esiste un adapter "non ancora inizializzato".
* **Le API crypto restano quelle del dominio.** Si usano solo i port `EnvelopeEncryptor` e `KeyDerivationService`: XChaCha20-Poly1305 AEAD con `AssociatedData` obbligatoria, nonce generato dall'adapter e chiavi come handle opachi (`SymmetricKey`). Non si usano `secretBox` (nessun dato associato, quindi nessun legame al record), né chiavi o nonce passati come `Uint8List`.
* **Audio come flusso di byte, mai come percorso di file.** Il port di registrazione restituisce `Stream<Uint8List>`, con chunk cifrati appena prodotti, così su nessuna piattaforma esistono file audio in chiaro. Implementazione con il pacchetto `record` (`startStream`). Nota: lo streaming di `record` produce PCM, quindi la compressione Opus va fatta dall'adapter (libopus via FFI su mobile, WebCodecs `AudioEncoder` su web). Safari non registra Opus/WebM con `MediaRecorder`; il formato effettivo va negoziato per piattaforma e salvato nei metadati cifrati del blob.
* **Permessi microfono:** Android `RECORD_AUDIO` in `AndroidManifest.xml`; iOS `NSMicrophoneUsageDescription` in `Info.plist`, localizzata in `ios/Runner/<lingua>.lproj/InfoPlist.strings`; web nessun manifest, ma solo su HTTPS (o `localhost`), con richiesta del browser a runtime.
* **Opus (decisione del 2026-10-11):** libopus si compila dai sorgenti ufficiali tramite il build hook di `blob_storage_media_adapters` (versione e SHA-256 fissati in `hook/build.dart`; la CI confronta l'hash con `SHA256SUMS.txt` di xiph.org). I binding FFI sono nostri e minimi, e i `ctl` variadici passano da un piccolo shim C. Nessun wrapper di terze parti. Per build offline: `MODUSNOTE_OPUS_ARCHIVE=/percorso/opus-<versione>.tar.gz` (l'hash viene verificato comunque). Sul web l'Opus arriva da WebCodecs (vedi "Audio nel browser"); dove manca, la cattura produce WAV PCM16 non compresso.

### Infrastruttura (decisione del 2026-10-11)
| Componente | Servizio | Cosa vede il servizio |
|---|---|---|
| Client web | **Cloudflare Pages** (file statici; build in GitHub Actions, perché l'ambiente di build di Pages non include Flutter, poi `wrangler pages deploy`) | Solo il bundle dell'app |
| Blob audio cifrati | **Cloudflare R2** (S3-compatibile, nessun costo di egress) | Solo chunk `.enc` e la loro dimensione |
| Sync e account | **Supabase** (PostgreSQL + Auth) | Righe cifrate, id, revisioni, timestamp; l'email dell'account |

L'invariante zero-knowledge vale per tutti e tre i servizi: ricevono e restituiscono solo ciphertext prodotto dalle buste del dominio. Regole che ne derivano:
* **Auth e chiavi sono separati.** Supabase Auth autentica l'account (email/magic link o OAuth) per l'accesso alle righe. La passphrase del vault non viene mai inviata, né usata come password di Supabase. Se in futuro si userà un'unica password, la credenziale di login deve essere derivata dalla chiave Argon2id con una derivazione separata (KDF con contesto diverso), mai la passphrase stessa.
* **Row Level Security** obbligatoria su ogni tabella: un utente legge e scrive solo le righe dei vault di cui è membro.
* **Metadati minimi in chiaro:** id opachi, revisione, timestamp di sync, dimensione. Titoli, tipi di nota, tag e schemi stanno solo dentro i payload cifrati.
* **R2 tramite URL pre-firmati** emessi da una funzione lato server (Supabase Edge Function o Cloudflare Worker) dopo il controllo dell'autorizzazione. Le credenziali R2 non arrivano mai al client. CORS limitato al dominio dell'app.
* **Cloudflare Pages senza iniezioni:** vanno disattivate tutte le funzioni che modificano l'HTML servito (Rocket Loader, Web Analytics automatico, Email Obfuscation, Zaraz), perché romperebbero CSP e SRI. CSP e altri header si dichiarano in `apps/modusnote/web/_headers`.
* **Fiducia nel codice servito:** Cloudflare, o chiunque abbia accesso al deploy, può servire un bundle diverso. Per questo valgono le mitigazioni della sezione "Client web" (hash delle build pubblicati, build riproducibili).
* **Schema (`supabase/migrations/`):** `workspaces`, `workspace_accounts` (account Supabase ammessi, con `can_manage`), e tre flussi **append-only**: `sync_rows` (record_id, epoca, ciphertext), `membership_records` (registro firmato, `sequence` univoca) e `key_bundles`. Nessuno può fare UPDATE o DELETE sui flussi, nemmeno con una policy aggiunta per errore, perché il privilegio è revocato. Le posizioni sono assegnate dal server per workspace sotto lock, quindi crescono in ordine di commit e un client che legge `position > cursore` non salta righe. Revocare un dispositivo significa anche togliere il suo account da `workspace_accounts`. `device_links` (migrazione `20261013000000_device_links.sql`) è l'unica tabella da cui si cancella: offerta e risposta di un collegamento tra dispositivi, leggibili solo dall'account che le ha scritte e solo per 15 minuti; il client sceglie solo `link_id`, tipo e payload (privilegio di INSERT per colonna), così una riga non può essere datata nel futuro.
* **Test RLS:** `supabase/tests/run.sh` applica le migrazioni a un PostgreSQL temporaneo con uno stub di `auth.uid()` ed esegue i test come ruolo `authenticated` con il `sub` del JWT, come fa PostgREST. Gira anche in CI.
* **Adapter Dart (`SupabaseSyncServer`):** parla con PostgREST (`/rest/v1/<tabella>`) tramite `package:http`, con la chiave anon pubblica e il token di sessione Supabase passato come callback (mai salvato né incluso nei messaggi d'errore). I `bytea` viaggiano come `\x` esadecimale. Le risposte sono input non fidato: posizioni non strettamente crescenti o registro di membership con buchi danno `MalformedSyncDataException`, una voce illeggibile viene scartata. Errori di rete, timeout, 5xx, 408 e 429 diventano `ServerUnavailableException` (il motore resta offline e riprova); gli altri rifiuti `SyncServerRejectedException(status)`. `supabase/tests/e2e.sh` lo prova contro PostgREST v12 e PostgreSQL veri (RLS, trigger, formati), anche in CI.
* **URL pre-firmati per R2 (`supabase/functions/blob-url`):** Edge Function senza dipendenze di terzi (firma SigV4 scritta con WebCrypto e verificata sul vettore d'esempio di AWS). Riceve `{workspace_id, blob_id, method}` con il token di sessione, chiede al database `is_workspace_account` *come il chiamante* (lo stesso helper delle policy RLS) e restituisce un URL valido 5 minuti per l'unico oggetto `<workspace>/<blob>.enc`. `GET` per leggere (anche a intervalli con `Range`), `PUT` solo per creare: l'URL è firmato con `If-None-Match: *`, quindi un membro non può sovrascrivere la registrazione di un altro. Nessun DELETE. I segreti `R2_*` si impostano con `supabase secrets set` e non lasciano mai la funzione; le risposte hanno messaggi fissi; CORS solo per `APP_ORIGIN` (predefinito `https://modus.serv.run`). Il CORS del bucket R2 deve ammettere la stessa origine e l'header `If-None-Match`. Limiti noti: un URL `PUT` pre-firmato non può imporre una dimensione massima (resta il limite di R2), e il rifiuto di sovrascrittura va confermato su un bucket reale al primo deploy.

### Vault del dispositivo
* **`VaultKeeper`:** `create` fonda uno spazio personale con una nuova identità di dispositivo, `unlock` lo riapre. La passphrase diventa la MasterKey (Argon2id) ed è consumata da ogni chiamata. La MasterKey sigilla l'identità e deriva la chiave locale dei record (`crypto_kdf`, contesto `mn-local`), poi viene rilasciata subito.
* **`VaultHeader`:** l'unico dato del vault in chiaro (salt, costi Argon2id entro soglia minima e massima, workspace, fondatore, `SubkeyId` della chiave locale, identità sigillata; un dispositivo che si è unito a un workspace scrive la versione 2 con il proprio `member`, mentre l'header del fondatore resta byte per byte quello di sempre). Tutti i campi sono legati ai dati associati dell'identità, quindi un header alterato si comporta come una passphrase sbagliata (`WrongPassphraseException`).
* **Registro locale:** registro dei membri e `KeyBundle` salvati sul dispositivo (`SqliteVaultStore`, stesso file SQLite dei record, schema versionato in comune) vengono riverificati a ogni sblocco a partire dal fondatore dell'header. Quello che il `SyncEngine` verifica dopo (record nuovi del registro, `KeyBundle` che concedono chiavi a questo dispositivo) si aggiunge con `appendMembership` e `appendKeyBundles`, così il vault si riapre offline sapendo tutto. `lock()` rilascia identità, chiave locale e GroupKey.
* **Limite noto (Flutter):** la passphrase digitata passa per la `String` di un `TextField`, inevitabile. La UI la converte subito in `PasswordSecret` e svuota il controller.
* **App (`lib/vault/`, `lib/bootstrap/`):** su mobile `VaultGate` chiede di creare il vault al primo avvio e la passphrase ai successivi, e mostra le note solo a vault aperto; il pulsante "Blocca" rilascia le chiavi. `VaultNoteStore` salva ogni nota come documento `EntryCodec` in un record del `SyncEngine` (l'id della nota è l'id del record, 32 cifre esadecimali) e scarta i record che non decodificano, non rispettano lo schema o portano l'id di un altro record. Il database è `vault.sqlite` nella cartella di supporto privata dell'app; il vault mobile usa Argon2id `moderate`. Senza progetto Supabase configurato il server di sync è `OfflineSyncServer`, sempre irraggiungibile: le modifiche restano nella coda, già sigillate (vedi "Account e sincronizzazione"). Sul web (Fase 7.1) lo stesso vault vive in IndexedDB: vedi "Vault nel browser".
* **Account e sincronizzazione (2026-10-13):** il progetto si fissa alla build con `--dart-define=MODUSNOTE_SUPABASE_URL=https://<progetto>.supabase.co` e `--dart-define=MODUSNOTE_SUPABASE_ANON_KEY=<chiave publishable>` (`lib/sync/sync_config.dart`: solo HTTPS, o HTTP verso `localhost`; senza i due valori niente account e niente pulsante). La chiave publishable è pubblica e viaggia solo nell'header `apikey`, mai come Bearer. L'accesso è un codice inviato per email (`SupabaseAuth`, GoTrue `/otp` e `/verify`; il codice arriva se i modelli "Magic Link" e "Confirm signup" contengono `{{ .Token }}`. Il piano gratuito di Supabase lascia i modelli predefiniti, che portano solo un link: in quel caso il link si copia dall'email e si incolla al posto del codice, e `verifyCode` ne usa solo l'hash del token, dopo aver controllato che punti a `/auth/v1/verify` del progetto, in HTTPS e per un accesso (`magiclink` o `signup`); il link non viene mai aperto), così non si apre nessun link e funziona uguale su telefono e browser. `SyncAccount` tiene la sessione solo a vault aperto: allo sblocco `VaultGate` la legge dall'impostazione `sync.session`, sigillata con la chiave locale (`VaultKeeper.saveSetting`, tabella `vault_settings`, schema locale v4, dati associati con nome e workspace), la rinnova un minuto prima della scadenza e la risigilla; al blocco la dimentica. Una sessione danneggiata vuol dire accedere di nuovo, mai un vault che non si apre. Senza sessione il token lancia `ServerUnavailableException`, quindi il motore resta offline. `SyncController` sincronizza allo sblocco e all'accesso, 2 s dopo l'ultima modifica salvata, ogni minuto e al ritorno in primo piano, una sincronizzazione alla volta; viene chiuso prima che le chiavi siano rilasciate, e quello che una sincronizzazione in corso fa dopo viene ignorato. Righe nuove ricaricano la libreria (`VaultNoteStore.reload`). Alla prima sincronizzazione il fondatore registra il workspace (idempotente: 409 è un successo) e pubblica il registro dei membri; il cursore `SyncStream.membership` conta quanti record il server ha, e un registro diverso già presente sotto lo stesso workspace è `LedgerRollbackException` (stato "dati non verificati"). Il pulsante cloud nella libreria mostra lo stato e apre il foglio di accesso. **Limite noto:** chi conosce l'id di un workspace e lo registra per primo lo blocca al proprietario. Sul web `connect-src` deve includere l'origine del progetto Supabase prima del deploy.
* **Registrazioni su R2 (2026-10-13):** con un progetto configurato, dopo ogni sincronizzazione riuscita `BlobSync` (`lib/sync/blob_sync.dart`) carica le registrazioni referenziate dalle note che il dispositivo ha e il server non ancora; quali sono già su R2 è un'impostazione sigillata del vault (`sync.blobs-sent`), così nulla parte due volte e un'impostazione danneggiata costa solo un ricaricamento innocuo. Una registrazione di un altro dispositivo si scarica alla prima pressione di play (`NotePlayback` con `ensureLocal`), non prima: meno traffico e nessuna richiesta che riveli quali note si aprono. Nel dominio `BlobReplication` (`blob_storage_media`, port `RemoteBlobStore`) copia solo ciphertext: il download entra nello store locale solo se è lungo esattamente quanto dicono i metadati della nota (`ChunkLayout.ciphertextLengthFor`), un server che manda di più viene fermato a quella soglia, e ogni chunk resta autenticato alla riproduzione; due play contemporanei condividono un download. L'adapter `R2RemoteBlobStore` (`blob_storage_media_adapters/lib/remote_blobs.dart`, su ogni piattaforma) chiede l'URL alla Edge Function `blob-url` con il token di sessione e poi parla direttamente con R2: il token non arriva mai a R2, un URL non HTTPS o con credenziali viene rifiutato, `PUT` con `If-None-Match: *` (412 = già caricato, quindi successo), corpo in streaming con `Content-Length`. Rete, 5xx, 408 e 429 sono `RemoteBlobUnavailableException` (la sincronizzazione resta "offline" e riprova; il player dice di collegarsi), gli altri rifiuti `RemoteBlobRejectedException`. **Limiti noti:** le registrazioni cancellate in locale restano su R2 (nessun DELETE, servirà una pulizia lato server); sul web `connect-src` dovrà includere anche l'origine del bucket R2.
* **Collegamento tra dispositivi (2026-10-13):** telefono e browser della stessa persona condividono un workspace; ogni dispositivo ha la propria identità e la propria passphrase. Dal foglio Sincronizzazione, a vault sincronizzato, «Collega un altro dispositivo» (`LinkDeviceSheet`) genera un `LinkCode` (10 simboli Crockford base 32, 50 bit) e `VaultKeeper.offerLink` pubblica un `LinkOffer`: l'`Invitation` (workspace e fondatore) sigillata con una chiave Argon2id del codice (sale casuale; i costi sono quelli della build, mai letti dal server) e dati associati con l'id del collegamento. Sul nuovo dispositivo, al primo avvio, «Collega a un vault esistente» (`JoinVaultScreen`) chiede l'accesso con la stessa email, il codice e una passphrase; la sessione resta in memoria finché il vault non esiste, poi viene sigillata come `sync.session`. `VaultKeeper.join` apre l'offerta più recente dell'account (altrimenti `LinkCodeRejectedException`), genera l'identità e pubblica un `LinkAnswer` con la sua `PublicIdentity` sotto la stessa chiave (dati associati diversi). `LinkOffering.poll` (ogni 2 s) ignora le risposte che non si aprono e chiama `SyncEngine.admit`: un record `MemberInvited` come owner, pubblicato, e un `KeyBundle` con tutte le epoche (`appendKeyBundle`, ora nel port `SyncServer`); ripetere è innocuo (`grantAll` se è già membro), così un'ammissione interrotta si completa al giro dopo. `LinkRequest.poll` crea il vault solo quando il registro del server si verifica contro il fondatore dell'offerta, il dispositivo è membro e ha la chiave dell'epoca corrente; il suo header è la versione 2, con il proprio `member` (la passkey controlla quello). Il server vede solo l'id del collegamento, le dimensioni e il ciphertext: per far passare un dispositivo suo dovrebbe indovinare il codice nei 10 minuti di validità, al costo di un Argon2id per tentativo. Il foglio tiene aperto il vault (`hold()`) e chiuderlo ritira il codice. Port `DeviceLinkChannel`, implementato da `SupabaseSyncServer` sulla tabella `device_links`. **Limiti noti:** può unirsi solo un dispositivo senza vault; serve lo stesso account Supabase su entrambi; le righe scadute restano nella tabella (invisibili) finché non ci sarà una pulizia lato server; un dispositivo ammesso e poi abbandonato resta membro finché l'app non saprà revocarlo.
* **Limite noto:** Argon2id gira sull'isolate della UI (le `SecureKey` non attraversano gli isolate), quindi lo sblocco blocca l'interfaccia per circa un secondo; la UI mostra prima l'indicatore di avanzamento.
* **Blocco automatico (decisione del 2026-10-11):** `AutoLock` (`lib/vault/auto_lock.dart`) chiude il vault dopo 5 minuti senza tocchi, tasti o modifiche e dopo 30 secondi in background (`hidden`/`paused`). Il background si controlla anche con l'orologio al ritorno, perché un processo congelato dal sistema non esegue timer. Tocchi e tasti si osservano a livello di binding (pointer router globale e `HardwareKeyboard`), la tastiera software tramite l'`onChanged` dell'editor. Mentre il foglio di registrazione è aperto il vault resta aperto (`hold()`), così la chiave non sparisce a metà di una registrazione. Prima di bloccare si chiudono tutte le schermate sopra la libreria, quindi nessuna nota decifrata resta visibile; una modifica non salvata va persa, come la registrazione di una modifica abbandonata.
* **Schermo privato (decisione del 2026-10-12):** su Android `MainActivity` imposta `FLAG_SECURE` prima del primo frame: niente screenshot, registrazioni dello schermo, trasmissione né miniatura tra le app recenti, sempre, anche a vault bloccato. iOS non permette di bloccare gli screenshot: `PrivacyCover` (in `AppDelegate.swift`) copre la finestra con Deep Void quando la scena smette di essere attiva, così il selettore delle app non mostra né fotografa le note. Ascolta le notifiche di `UIScene` invece di sovrascrivere `FlutterSceneDelegate`, che inoltra il ciclo di vita al motore (e quindi ad `AutoLock`). Sul web non esiste un equivalente. `test/platform/screen_privacy_test.dart` controlla i sorgenti nativi.
* **Tipi di nota, icone e colori (decisione del 2026-10-11):** ogni schema può nominare un'icona (`NoteIcon`) e un colore d'accento (`NoteTint`). Sono nomi, non immagini né colori: l'app li traduce in `lib/notes/note_appearance.dart` e un nome sconosciuto (da un'app più nuova) viene ignorato. Canzone: nota musicale, viola. Sogno: luna, rosa. To-do: lista con caselle, ciano. Appunto: matita, oro. Filtri e scelta del tipo li mostrano; ogni colore è testo AA su entrambi gli sfondi (`theme_test`). La card della libreria è tutta colorata (decisione del 2026-10-13): Abyssal Slate velato dal colore del tipo a 1/φ⁴ (`NoteAppearance.wash`), il massimo che tiene in AA testo, data e avanzamento; l'icona resta nel colore pieno, l'etichetta del tipo è Dust Silver (il viola su card viola andrebbe sotto AA). Il titolo mostra solo righe intere e la card si allunga oltre φ : 1 solo quando la dimensione del testo di sistema non lascia spazio a tipo, una riga di titolo e data.
* **To-do come lista (decisione del 2026-10-11):** `task` v2 ha un titolo facoltativo e un campo `ChecklistFieldType` (task di una riga, al massimo 200, 500 caratteri ciascuno, niente caratteri di controllo o bidirezionali). Nell'editor Invio aggiunge un task sotto quello corrente e Invio su un task vuoto lo toglie e chiude la lista; i task vuoti non entrano mai nel valore. Le note `task` v1 si leggono tramite `SeedSchemas.catalog` (`SchemaCatalog` + `SchemaMigration` con `DeriveField`): la descrizione, resa una riga sicura, diventa l'unico task e "completata" il suo stato. La nota viene mostrata come v2 senza toccare revisione e data, e riscritta come v2 solo al salvataggio successivo, così aprire l'app non riscrive le note su ogni dispositivo.
* **Anteprima Markdown (decisione del 2026-10-11):** i campi `MarkdownFieldType` hanno le schede Scrivi/Anteprima (una nota già scritta si apre sull'anteprima). Il parser è nostro (`lib/notes/markdown/markdown_document.dart`, nessun pacchetto di terzi) e costruisce solo un albero: titoli, paragrafi, elenchi anche annidati e con caselle, citazioni, codice, righe, grassetto, corsivo, barrato, codice in linea, link e immagini. `MarkdownView` lo disegna con widget. L'HTML resta testo, i link mostrano l'indirizzo accanto al testo e non si aprono, le immagini non vengono mai scaricate (si vede solo il testo alternativo), perché una nota arriva da altri membri e una richiesta di rete rivelerebbe chi la legge. Annidamento limitato a `MarkdownDocument.maxDepth` (8) e scansione lineare: la nota più lunga ammessa (100.000 caratteri) si legge in tempo lineare qualunque cosa contenga. Le card della libreria mostrano il testo senza markup (`plainText`).
* **Registrazioni nelle note:** il payload cifrato di ogni nota è un `RecordedNote` (`RecordedNoteCodec`): l'entry più i `BlobMetadata` di ogni blob che referenzia, ciascuno con l'epoca della GroupKey da cui deriva la sua BlobKey (la nota viene risigillata alle epoche nuove, il blob no). Un blob referenziato senza metadati, o metadati per un blob non referenziato, rendono la nota illeggibile. `NoteRecorder` registra dal microfono direttamente in un blob sigillato con la GroupKey corrente (`SyncEngine.contentKeyFor`); le registrazioni sostituite, tolte o di una modifica abbandonata vengono cancellate dopo il salvataggio, e i `.enc.part` lasciati da un crash all'avvio.
* **Riproduzione (decisione del 2026-10-11):** `RecordingPlayback` decifra il blob con la GroupKey della sua epoca (ogni chunk è autenticato prima che il decoder lo veda) e lo decodifica tutto in memoria: Ogg Opus con la nostra libopus (`OpusAudioDecoder`, su un isolate a parte), WAV PCM16 del web con `WavAudioDecoder`. Il demuxer Ogg accetta solo ciò che scrive il nostro muxer (un flusso logico, CRC, sequenza, nessun pacchetto spezzato tra pagine, OpusHead mono/stereo, famiglia 0, guadagno 0) e rifiuta tutto il resto come `MalformedBlobException`. La riproduzione è limitata a 30 minuti (`DecodedAudio.maxDuration`), controllati sul granule prima di decodificare. Il PCM diventa un WAV in memoria passato a **flutter_soloud** (versione fissata, `LoadMode.disk` per non espandere a float) dietro il port `RecordingPlayer` dell'app: nessun file in chiaro, nessun socket. Nel pubspec radice `hooks.user_defines.flutter_soloud.no_xiph_libs: true`, altrimenti il build hook scaricherebbe librerie Xiph precompilate senza hash fissato. Niente si decifra finché l'utente non preme play, e i campioni si liberano quando il campo esce dallo schermo. Sul web flutter_soloud porta con sé i suoi `.wasm` precompilati ma non vengono caricati (servono gli script in `index.html`): il player web è Web Audio (vedi "Audio nel browser").
